# T03 · 공유 숫자 동기화 구현 결정

2026-09-12. 이 문서는 T03 구현의 계약과 제한을 설명한다. 소스 존재나 설계 검토를 실행 성공으로 기록하지 않는다. 실제 Compile·자동 시험·별도 프로세스·앱 빌드·실기기 결과는 [VALIDATION.md](VALIDATION.md)의 해당 실행과 증거를 따른다. T02 연결 성공은 T03 데이터 정합성 또는 두 iPhone의 G2 통과를 대신하지 않는다.

## 목적과 범위

T02의 `DirectConnectionSession`과 설치된 NGO 2.13.1 / Unity Transport 6.5.0을 재사용한다. 참가자는 Host와 Client 두 명이다. 공유 숫자에 대한 요청·호스트 확정·응답·상태 일치를 검증한다. 구슬·전투·자동 방 탐색·자동 재접속·NetworkObject 생성·범용 메시지 프레임워크는 추가하지 않는다.

구현 근거는 `Assets/_Project/HapioMVP/Networking/Counter/CounterAuthority.cs`와 `CounterSync.cs`다. 기존 연결 컴포넌트는 자신이 소유한 `OwnedManager`를 읽기 전용으로 노출하고, 카운터는 해당 Manager에만 메시지 핸들러를 연결한다.

## 호스트가 확정하는 요청

양쪽의 +1 버튼은 `RequestIncrement()`를 호출한다. Client는 요청을 보낸 후 호스트의 전체 상태나 처리 응답을 기다리며, 공유 숫자를 먼저 올리지 않는다. Host의 자체 입력도 원격 입력과 동일한 `CounterAuthority.Apply(actualSenderId, sessionId, requestId)`를 통과한다.

송신자 ID는 NGO 수신 콜백의 실제 송신자에서 얻는다. 요청 패킷에는 송신자 ID를 넣지 않는다. 연결에 등록된 참가자인지 확인한 뒤 권위 모델에서도 현재 참가자·세션을 검사한다. Client는 ServerClientId인 0에서 온 상태와 처리 응답만 받는다.

Host는 연결 세션마다 새로운 GUID를 생성한다. 요청 ID는 각 참가자가 해당 세션에서 1부터 증가시키는 `ulong`이다. 처리 기록의 키는 `(actualSenderId, sessionId, requestId)`다. 서로 다른 참가자가 같은 숫자의 requestId를 사용하는 것은 별개의 요청이다.

## T03 전용 메시지 네 가지

모두 NGO `CustomMessagingManager`와 `ReliableSequenced`를 사용한다. 이것만으로 처리 중복 제거가 완성되는 것은 아니므로, 권위 모델이 별도로 요청 기록을 관리한다.

| 메시지 | 방향 | 내용과 역할 |
|---|---|---|
| `C6.T03.SnapshotRequest.v1` | Client → Host | 이번 연결의 초기 상태 요청용 nonce |
| `C6.T03.Snapshot.v1` | Host → Client | nonce와 전체 공유 상태 |
| `C6.T03.Request.v1` | Client → Host | sessionId와 requestId, 연산은 +1로 고정 |
| `C6.T03.Receipt.v1` | Host → 요청자 | nonce, 처리 당시 상태, 송신자·요청 ID, 승인·중복 여부, 사유 |

메시지는 고정된 목적의 이진 형식이다. 버전·길이·GUID·응답 플래그·사유 길이·상태 불변식을 확인한다. 초기 요청은 17바이트, 증가 요청은 25바이트, 전체 상태는 65바이트, 처리 응답은 최대 179바이트다. 쓰기 버퍼 상한은 192바이트이며 사유 문자열은 ASCII 96바이트 이하로 제한한다. 잘못된 길이와 여분의 데이터는 상태로 적용하지 않는다.

## 초기 전체 상태와 연결 수명

Host는 혼자 연결을 열어 둔 상태에서도 숫자를 증가시킬 수 있다. Client는 메시지 핸들러를 등록한 다음 전체 상태를 명시적으로 요청하고, 그 상태를 받은 뒤 +1 입력을 활성화한다. 따라서 참가 전에 Host가 바꾼 값도 초기 전체 상태에 포함한다.

Client는 연결마다 새로운 nonce를 만들고, Host는 해당 참가자의 응답과 전체 상태에 이 nonce를 포함한다. Client는 자신의 현재 nonce가 맞는 메시지만 받는다. 세션 ID 검사와 함께 이전 연결의 초기 상태나 처리 응답이 새 연결을 초기화하는 것을 막는다. 초기 상태 요청은 같은 연결에서 1초 간격으로 최대 8번 전송한다. 이는 상태 초기화 재요청이며 자동 재접속이 아니다. 이후에도 초기 상태가 없으면 사용자가 연결을 끝내고 수동으로 참가해야 한다.

이전 세션의 요청은 권위 모델에서 거부한다. 이 거부에는 현재 모델의 상태가 담기므로, 서비스는 요청의 sessionId와 응답 상태의 sessionId가 다르면 현재 nonce를 붙인 응답을 전송하지 않는다. 이전 요청의 ID가 새 세션의 미응답 요청 ID와 같더라도 새 요청을 응답 완료로 잘못 처리하지 않게 하는 조건이다.

연결 종료 시 처리 기록·미응답 요청·응답 완료 기록·참가자 nonce·표시 상태를 지운다. Manager 또는 CustomMessagingManager가 바뀌면 기존 메시지 핸들러를 해제한 뒤 새 객체에 연결한다. 바인딩 교체 도중에는 외부 변경 이벤트를 발행하지 않는다. 카운터 컴포넌트를 비활성화할 때도 살아 있는 연결을 종료해, 같은 연결 안에서 Host 권위 모델만 새로 만들어지는 상황을 피한다.

## 중복 응답과 현재 상태

같은 키가 다시 오면 공유 숫자·승인 수·거부 수·revision을 바꾸지 않고 원래 처리 결과를 반환하며 `Duplicate=true`를 표시한다. 원래 결과에 들어 있는 상태는 이후 처리된 요청들보다 과거 상태일 수 있다.

Client는 자신의 미응답 요청에서 처음 확인한 유효 응답만 응답 완료 수에 더한다. 이미 응답한 요청의 재수신은 다시 더하지 않는다. 과거 응답을 확인해도 현재 화면의 상태를 과거로 되돌리지 않는다. 상태는 같은 세션에서 revision이 감소하지 않아야 하며, 값·승인 수·거부 수도 감소하지 않아야 한다. 같은 revision인데 값이나 카운터가 다른 상태는 거부한다. Host는 처리 응답과 별개로 자신의 최신 전체 상태를 배포한다.

## 표시 숫자의 의미

| 표시 값 | 집계 기준 |
|---|---|
| 공유 값 `Value` | 호스트가 승인한 고유 +1 요청 수 |
| 호스트 승인 수 `ApprovedCount` | 현재 세션에서 기록한 고유 승인 수. 공유 값과 같아야 함 |
| 호스트 거부 수 `RejectedCount` | 현재 참가자·현재 세션에서 추적 기록에 남긴 고유 거부 수 |
| `Revision` | 추적된 승인 또는 거부로 권위 상태를 바꾼 횟수. 승인 수 + 거부 수 |
| 내 고유 요청 수 `SentCount` | 로컬에서 새 요청 ID를 할당해 제출한 수. 전송 실패 가능성까지 포함하며 도착 증거가 아님 |
| 내 응답 완료 수 `AcknowledgedCount` | 해당 로컬 요청에 대해 유효 응답을 처음 확인한 수. 승인과 거부 모두 포함 |
| 내 대기 수 `PendingCount` | 제출했으나 유효 응답을 아직 확인하지 못한 고유 요청 수 |
| 중복 응답 수 `DuplicateReceiptCount` | 이미 응답한 요청의 재수신 또는 Duplicate 표시 응답의 관측 수 |

개발용 마지막 요청 재전송은 동일한 requestId를 사용한다. 고유 요청 수와 고유 응답 완료 수를 추가로 늘리지 않는다. 실제 전달·승인 여부는 호스트 기록, 응답 완료 수, 대기 수, 양쪽 최종 상태를 함께 확인해야 한다.

현재 요청 연산은 +1 하나이고 일반 버튼은 1 이상의 ID만 만든다. 유효 참가자가 현재 세션에서 예약 ID 0을 처음 보낸 경우는 `invalid-request-id`로 추적하며 거부 수와 revision만 1 증가한다. 같은 ID 0의 반복은 원래 거부 결과를 반환한다. 비참가자·이전 세션·종료된 세션·기록 용량 초과는 권위 모델의 값·카운터·revision·처리 기록을 바꾸지 않는다. 잘못된 패킷도 상태에 포함하지 않는다. 따라서 화면의 거부 수는 모든 네트워크 오류나 버려진 패킷의 총합이 아니다.

## 개발용 기록 제한

`CounterAuthority.DefaultMaxTrackedRequests = 10000`은 `DEMO_ASSUMPTION`이다. 현재 세션 전체의 처리 기록 용량을 제한해 메모리 사용을 유한하게 만든다. 세션 도중 오래된 기록을 제거하면 같은 요청을 다시 적용할 수 있으므로, 용량이 차면 새 고유 요청을 `ledger-full`로 거부하고 기존 키의 결과는 계속 반환한다.

각 참가자의 로컬 고유 요청 할당 제한도 같은 원본 상수를 참조한다. 이것은 참가자마다 10,000건의 승인을 보장한다는 뜻이 아니다. Host와 Client가 공유하는 권위 모델 전체가 10,000개 기록을 사용하므로, 두 참가자의 합계가 먼저 전체 한도에 도달할 수 있다. 한도를 늘릴 때는 중복 방지 기록의 메모리 사용과 용량 거부 시험을 함께 검토한다. 이 값은 게임 밸런스 설정이나 G2의 100개 요청 조건이 아니다.

## 실행 기록과 실기기 조건

2026-09-13 후속 적용: 사용자의 요청에 따라 이번 G2를 iPhone17+iPad로 변경하고 빌드5에서100건·첫 권한·실패 후 수동 재시도를 실제 확인했다. [기기 조건 변경](G2_DEVICE_CHANGE.md)과 [현재 VALIDATION](VALIDATION.md)이 최신 판정이다. 아래 최초 작성 시점의 두 iPhone 미실행 설명은 역사적 상태이며 현재 변경된 Gate를 차단하지 않는다.

권위 모델 시험은 순차·동시·중복·송신자·이전 세션·종료·용량 조건을 다룬다. 패킷 시험은 경계 길이·버전·전체 상태·응답 필드·잘못된 상태를 다룬다. 테스트 코드가 있다는 사실만으로 시험 실행이나 네트워크 경로를 통과했다고 기록하지 않는다. 실제 실행 수와 누락·실패는 XML과 실행 로그로 확인한다.

이 결정 문서 작성 시점에 **두 iPhone의 G2 실기기 데이터 시험과 최초 로컬 네트워크 권한 요청 시나리오는 NOT_RUN**이다. 같은 Wi-Fi의 실제 iPhone 두 대에서 총 100개의 고유 요청을 처리하고, 응답 확인 뒤 양쪽 값이 호스트 승인 수와 일치하는지 확인해야 한다. 이는 연결을 100번 반복하는 시험이 아니다. 권한 첫 요청과 연결 실패 후 수동 재시도도 별도 증거가 필요하다. Mac 자동 입력 결과와 실제 iPhone 입력 결과를 구분하며, 이전 Task의 결과를 이번 빌드에 승계하지 않는다.

G2 결과를 [VALIDATION.md](VALIDATION.md)에 기록한 뒤 다음 Task 가능 여부를 판단한다. 이 문서와 T03 작업은 T04 자동 시작을 허용하지 않는다.
