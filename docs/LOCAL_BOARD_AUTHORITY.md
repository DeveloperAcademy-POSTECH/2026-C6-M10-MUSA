## 1. 처리 주체

| 범위 | 개인 기기 | Host 최종 확정 |
| --- | --- | --- |
| 조합판 | 드래그·굴림·마찰·충돌·곡선 경계·접촉/드롭 조합 위치 | 구슬 ID·종류·소유자·수명·소비 여부 |
| 생성 | 입력 즉시 임시 생성 표시 | 북 소유권·스태미나·보관 한도·생성 종류/잠금/발사 난수 |
| 조합 | 두 재료를 숨기고 움직일 수 있는 임시 결과 표시 | 음양 조건·재료 동시 소비·새 ID·오행 추첨 |
| 전달 | 경계 통과 감지·송신 화면의 대기 표시 | 방향·이웃·보관 한도·소유권 변경·아이템 잠금/릴레이·북 도착 방식 |

일반 드래그와 조합판 물리는 개편 전에도 로컬이었다. 이번에는 조합·투척 등의 화면 반응과 소유권 확정 통신을 분리하고, 평상시 조합판의 `motion_batch` 전송을 제거했다. Host가 모든 기기의 조합판 물리를 다시 계산하는 구조는 아니다. 로컬 겹침·폭발 영향 대상의 기하 판정은 해당 기기의 보고를 사용하고, Host는 소유권·종류·수명·발생한 폭발 등 논리 조건을 검증한다.

### 유지한 게임 규칙

- 현재 Lab의 **Raw Yin + Raw Yang** 조합 규칙을 따른다. 과거 프로토타입의 로비 속성 선택·자기 속성 공격 제한을 되살리지 않는다.
- 생성 추첨은 기존 플레이어별 승인 생성 순번, 조합·시크릿 상자 속성은 기존 공통 `combinedCount`, 북 도착 추첨은 기존 `drumHandoffCount`를 유지한다. 임시 구슬의 색·종류를 확정 결과로 간주하지 않는다.
- 북 소유자만 생성, 보관 한도와 스태미나 비용/회복, 아이템 잠금·해금·릴레이 단계·폭탄 수명, 직접 전달과 폭발/통과 북의 넘기기 제한 예외를 유지한다.
- 실제 투척자 기준 보상과 무늬, 축소/불 상태의 전달·조합 상속, 발사 시점 콤보 크기 배율, Paint/Crack의 서로 다른 승리 판정도 Host 경로를 유지한다.
- 최신 main의 #235 구슬 종류별 수명·마지막 소멸 예고·Host 만료 알림/연기를 보존한다. 조합·전달·투척 소비를 수명 만료로 표시하지 않는다.
- #241의 콤보 예고(`comboWarningAt`/`comboNextAt`)와 예고 HUD, `Combo Warning (seconds)` 공유 설정(170번째/인덱스169)을 보존한다. 현재 main 기본값인 콤보 ON·반복15초·페널티0.1배·보상2.5배를 #240의 과거 기본값으로 되돌리지 않는다.
- 전원 일시정지·같은 방 로비 복귀·DEV 재시작과 선택한 P번호의 고리 순서를 유지한다. 게임 시간은 Host 전투 시계이며 통신 재시도는 멈추지 않는 실제 시계를 사용한다.

## 2. 입력부터 확정까지

`LabNetwork.SubmitBoardAction`이 요청을 등록하고 로컬 표시를 먼저 시작한다. `LabLocalActionCoordinator`는 입력 구슬과 임시 ID 및 후속 동작의 의존 관계를 기록한다. 조합 결과를 승인받기 전에 옮기거나 던진 경우, 새 ID가 확인되면 그 ID로 후속 요청을 보낸다. 생성 종류·오행·아이템 해금 등 Host의 미확정 난수 결과를 로컬에서 새 규칙으로 결정하지 않는다.

Host는 요청의 설정 지문·전투 상태·소유권 세대와 실제 게임 규칙을 검사한다. `LabModel.TryCombineAt`·`TryUseItemAt`·`TryTransferAt`은 해당 행동의 실제 로컬 좌표를 받아 처리한다. 전달은 이전 `motion` 패킷 도착을 전제로 하지 않는 한 요청이다. 기존 공개 메서드 오버로드는 기존 검사와 호출의 동작을 보존한다.

`LabActionReceipt`는 승인/거절, 생성·변경·제거 ID, 플레이어 자원, 임시 ID 대응을 전달한다. 승인 시 임시 표시를 확정하고, 거절 시 관련 입력과 의존 동작을 복원한다. 투척 시 Host의 확정 투사체 알림이 돌아와도 이미 만든 로컬 시각 투사체를 다시 만들지 않는다. 확정된 색·축소·콤보 배율을 시각 투사체에 반영한다. 피해·도색·명중 보상은 로컬 예상 투사체가 만들지 않는다.

### ID·중복·복구

| 구분 | 의미와 적용 경계 |
| --- | --- |
| 행동 ID | `sessionId + round + sender + requestId`. 같은 요청을 재전송할 때 본문도 바꾸지 않는다. |
| 소유권 세대 | `LabOrbState.ownershipVersion`. 1부터 시작하며 승인된 전달에만 증가한다. 같은 기기로 돌아온 구슬에도 이전 방문의 요청을 사용할 수 없다. 일반 위치/메타데이터 `revision`과 다르다. |
| Host 결과 원장 | `LabActionResultLedger`. 같은 ID·본문에는 저장된 결과를 다시 보내고, 다른 본문 재사용은 거절한다. 최대 4,096개이며 미확정 결과를 임의로 쫓아내지 않는다. |
| 로컬 재시도 | 기본 최대 6회, 0.25초에서 최대 2초로 간격 증가. 소진 후 `action_query`로 Host 결과를 확인한다. Host에 기록이 없으면 동일한 고정 요청의 재전송을 요청한다. |
| 조합판 순번 | 수신자별 행동 결과와 조합판 프레임이 같은 `sequence`를 쓴다. 거절 결과도 한 순번을 차지한다. 오래된 결과를 현재 보드에 덮어쓰지 않는다. |
| 누락 복구 | 순번이 비면 조합판 체크포인트를 요청한다. 복구 중에는 새 입력·명령을 막고 기존 자유 구슬 물리는 계속 진행한다. 확인 없이 구슬을 재생성하거나 소유권을 원상복구하지 않는다. |

결과를 이미 적용했더라도 임시 ID 대응과 후속 요청 해제는 별도로 처리한다. 늦은 전체 스냅샷이 소비·전달된 구슬을 다시 보이게 하지 않도록 보드 원장과 제거 기록을 우선한다.

## 3. 조합판과 공동 상태의 전송 분리

### 조합판/행동 제어

`LabBoardPublisher`는 받는 사람의 조합판 구슬과 모든 북의 메타데이터를 전송한다. 새 구슬·새 소유권에는 초기 위치/속도가 포함되며, 평상시 위치·속도·위치 갱신 `revision`만 달라진 경우 델타를 만들지 않는다. 플레이어 자원·시계·일시정지·넘기기 제한·박의 시각 자세도 작은 프레임으로 전달한다.

첫 전송·새 판·5초 경과·명시 요청에는 보드 체크포인트를 보낸다. 보드 프레임과 행동 결과는 기존 NGO 신뢰성 제어 통신을 사용한다. 프레임은 4,096문자 단위로 나눠 모두 도착한 뒤 적용한다. 최대 4,096개 상태/제거 ID·5명·북 5개 및 전체 크기 제한은 패킷 안전 한도이며, 게임의 보관 한도를 대신하지 않는다. 박 폭탄이 가득 찬 판에도 떨어지는 규칙을 막지 않는다.

`LabBoardReplica.Overlay`는 로컬 구슬·모든 북과 더 최신인 제어 데이터를 공동 스냅샷에 합친다. **요괴 HP·도색 지도·진행률·콤보 결과·최종 Victory/Defeat는 이 프레임에서 만들지 않는다.** 최종 도색과 결과는 같은 검증된 트랜잭션으로 표시한다. 제어 프레임으로 종료를 먼저 알았으면 그동안 입력은 막는다.

### 도색/공동 스냅샷 Bulk

도색과 큰 스냅샷은 `C6Lab.Bulk.1` 메시지를 통해 NGO의 **Unreliable 파이프라인**으로 보내며, `LabBulkSender`/`LabBulkReceiver`가 애플리케이션 수준의 순서·재전송·누적 ACK를 제공한다. 앞 도색 조각의 재전송 때문에 NGO 신뢰성 제어 파이프라인의 후속 행동이 함께 기다리는 상황을 줄이기 위한 분리다. 동일 Wi-Fi의 대역폭이나 CPU까지 독립되는 것은 아니다.

| 항목 | 현재 제한/동작 |
| --- | --- |
| 전송 단위 | 필드를 줄인 DTO의 Base64 논리 본문을 `index\|count\|data`로 분할. 한 조각은 접두부 포함 최대 900문자이며 실제 외부 봉투+길이 필드도 1,200바이트 이내로 검사. 논리 본문 상한 32,768문자/64조각. |
| 송신 대기 | 기기별 최대 4 MiB. ACK 전 조각을 버리지 않으며 초과 시 새 enqueue를 거절. |
| 전송 창 | 기기별 32조각. 수신 재정렬 버퍼 최대 64조각. |
| 재시도 | 0.25 → 0.5 → 최대 1초. 누적 ACK로 연속 수신한 조각만 제거. |
| 처리 예산 | 한 호출·한 상대당 본문 최대 16,384바이트. 예산보다 큰 조각을 억지로 보내지 않음. |
| 수명 | Bulk 순번은 연결 단위. 같은 방의 새 판·로비 복귀에서 임의로 1로 되돌리지 않음. 연결 종료 시 정리. |
| 수신자별 합치기 | 그 사람에게 아직 미확인 Bulk가 있으면 새 공동 전송 묶음을 쌓지 않고 다음 기회에 최신 상태를 선택. 다른 사람의 상태·행동 프레임은 별도로 진행. |

도색 publisher도 기기별로 갖는다. 느린 기기에 건너뛴 변경이 있어도 그 기기가 마지막으로 받은 지도에서 시작하는 델타를 만든다. 초기/복구는 전체 지도이며, 그 뒤 공동 스냅샷에서 매번 모든 조합판을 반복하지 않는다. 최대 256×128 RGBA+P번호 전체 지도는 2,048문자 기준 **107개의 도색 조각**이다. 각 도색 조각의 DTO를 다시 900문자 이하 전송 조각으로 나누고, Bulk의 순서 복구 후 논리 본문을 재조립해 도색 수신기에 전달한다. Unity Transport의 6 KiB 설정과 별개인 NGO의 비분할 메시지 크기 제한을 지키기 위한 분할이며, MTU를 늘리지 않는다. 해상도·도색량·규칙은 바꾸지 않았다.

폭탄 만료·드롭 알림은 관련 보드 상태가 제거·추가되기 전에 처리한다. 폭발 중심과 영향 대상은 보유 기기의 실제 물리 위치를 사용하며, 임시 구슬이 포함되면 확정 ID 대응을 기다려 보고한다.

### 단독 개편 관측 수치의 의미

개편 전 Mac 앱 2개에 한 방향 60 ms·지터 ±10 ms·데이터그램 1% 손실 확률을 주는 프록시를 적용한 기준 기록에서, 참가자의 조합 표시가 약 151.8/167.7 ms(2회), 투척 표시가 약 171.3 ms(1회) 뒤 관찰됐다. 전달은 수신 기기의 오브젝트를 관찰하기까지 약 266.5 ms였으며 파일 조회 지연도 포함한다. 이는 문제를 재현한 소수 사례이며 평균·p95·휴대폰 지연 수치가 아니다.

개편 후의 구조적 목표는 입력 경로에서 임시 조합·시각 투척을 만드는 것이다. 같은 호출 안에 오브젝트가 생겼다는 관측은 실제 화면 표시나 터치 지연이 0 ms라는 뜻이 아니다. 확정 오행·명중·수신자 전달에는 통신 시간이 남는다. 개편 후 Mac 2인 직접 연결, 같은 지연/손실 2인, 직접 3인·5인 네 그룹에서 조합 표시 8회·비행 표시 8회가 입력 처리 호출 안에서 생성됐다. 지연 그룹의 조합 승인 2회는 약 169.4/170.3 ms 후 도착했다. 전달의 파일 조회 기반 샘플은 편차가 크므로 전달 속도 개선률을 주장하지 않는다.

- `LastActionRoundTripMilliseconds`: 로컬 등록부터 결과 도착까지의 시간. 의존 동작 대기 등이 포함될 수 있어 순수 네트워크 RTT로 읽지 않는다.
- `ActionRequestTransmissions`·`ActionReplayedResults`·`ReceivedBoardFrames`: 해당 애플리케이션 경로의 카운터다.
- `SentControlBytes`·`SentBulkBytes`: 코드에서 송신한 본문/길이 필드 기준이다. 모든 UDP/NGO 헤더·내부 전송 재시도까지 측정한 회선 사용량은 아니다.

## 6. 남은 한계와 확인 항목

- 실제 기기·핫스팟, 3~5대 휴대기기의 장시간 부하, 저성능 기기의 프레임/GC·열·배터리, 반복 지연 분포는 별도 실행 근거가 필요하다. 한 Mac의 독립 앱 3/5개 실행은 휴대기기 부하 검증이 아니다.
- 수신자에게 구슬이 최초 도착하는 시간과 Host의 공동 명중 확정 시간은 제거할 수 없다. 로컬 예상과 확정 결과가 다르면 보정할 수 있다.
- 큰 보드 체크포인트는 여전히 NGO 신뢰성 제어 통신에 분할 전송한다. 매우 많은 구슬·폭탄이 있으면 그 제어 큐에서도 순서 대기가 생길 여지가 있다. 이번 분리는 큰 도색/공동 스냅샷을 먼저 분리한 범위다.
- Bulk의 순서 대기는 해당 Bulk 스트림 안에는 남는다. 통신 정체 시 큰 공동 지도/결과가 늦게 도착할 수 있으며, 지도 일부를 완료된 결과처럼 표시하지 않는다.
- Host 교체, 끊긴 판의 자동 재접속/복원, 전용 서버 전환, 완전한 물리 되감기와 재실행은 구현하지 않는다. 기존 세션 종료/로비 처리 규칙을 따른다.
- 이 구조는 기존 협동 게임의 기기 보고 신뢰 범위를 유지한다. 실제 조합 겹침이나 폭발 충돌을 Host에서 독립적으로 재현하는 강한 부정행위 검증을 추가한 것은 아니다.


## 7. 실기기 확인 순서 — 아직 미실행

1. Host와 참가자에게 프로토콜 5649·170개 설정의 같은 통합 빌드를 설치한다. 일반 LAN과 iPhone 핫스팟을 각각 별도 시험하며, 기존 방 검색·직접 주소 연결 경로를 사용한다.
2. 목표 인원을 정하고 서로 다른 P번호를 선택한다. Host도 P1 이외 번호를 사용해 좌우 P 고리가 유지되는지 확인한다.
3. 북을 가진 참가자에서 생성한다. 승인 전 표시는 생성 예고이며, 확정된 음양·아이템 추첨은 Host 결과를 따른다. 북을 빠르게 누르거나 넘겨도 자원·개수·ID가 중복되지 않아야 한다.
4. 참가자의 Raw Yin/Yang을 드래그 조합하고 바로 임시 결과를 움직이거나 투척한다. 조합/비행 표시는 먼저 시작하고, 확정 뒤 오브젝트가 두 개가 되거나 이전 재료가 다시 나타나지 않아야 한다.
5. 구슬과 북을 좌우로 보내 같은 ID·소유권이 한 번만 옮겨지는지 확인한다. 수신 전까지의 통신 지연은 남으며 화면 전달 자체를 로컬 확정하지 않는다.
6. 승인 명중 뒤 모든 기기의 HP·도색 색상/P무늬·진행률이 일치하는지 확인한다. 일시정지·재개·DEV 재시작·같은 방 로비 복귀와 새 판을 확인한다.
7. 지연/손실 상태에서 위 조작을 반복하고, 거절·복구 중 구슬이 복제되거나 소비된 구슬이 돌아오지 않는지 확인한다. 실제 모바일 프레임/할당·발열과 반복 지연은 별도 계측한다. Mac loopback 결과로 이 항목을 통과 처리하지 않는다.
