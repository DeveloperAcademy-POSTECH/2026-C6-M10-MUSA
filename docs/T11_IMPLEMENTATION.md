# T11 구현 범위와 적용 차이

실제 프로젝트는 `/path/to/2026-C6-M10-MUSA`이며 T11 좌우 전달 하나를 구현했다. 실행 결과는 [T11_VALIDATION.md](T11_VALIDATION.md), 조작·재현 절차는 [T11_RUNBOOK.md](T11_RUNBOOK.md)를 따른다.

## 기존 동작과 새 씬

`OrbTransferBuild`는 저장된 `TwoPlayerBattle.unity`에서 별도 `OrbTransferBattle.unity`를 만들고 카메라·몬스터·입력·로비 참조를 다시 연결한다. 기존 씬·meta와 Config 원본은 보존한다. 새 씬에서만 `T10GameSession.transfersEnabled`를 켜고 빌드16으로 로비의 빌드 일치를 확인한다. 기존 씬의 전달 기본값은 false다. 새 카메라, 새로운 물리 공유 방식, 3인 이상 기능을 추가하지 않았다.

시작 구슬0, 스태미나100, 생성1개/비용20, 연속 회복20/3초, 유효한 Host 실제 피격의 공격자 회복5/최대100은 그대로다. Config의 수평 거리 .18·우세1.25·구슬 반지름비 .055를 사용하며 패키지 버전을 변경하지 않았다.

최신 사용자 지시의 자유 조합을 적용해 `OrbGestureEngine`에 선택적인 가장자리 손 떼기 조건을 추가했다. T11에서만 화면 끝까지 끌어 놓으면 전달한다. 중간의 긴 가로 드래그는 자유 배치이며, 다른 구슬에 놓으면 조합 또는 조합 거부가 우선한다. Combined의 실제 상단 경계 통과 발사는 그대로 우선한다. 별도 속도 기준·조합 전용 존은 없다.

## 전달 승인과 상태 동기화

`HostOrbRegistry.TryCompleteReservedTransfer`는 정확한 기존 reservation을 확인한 뒤 같은 ID·종류·음양의 owner를 한 번에 바꾸고 잠금을 해제한다. 보관 상한은 Idle과 Launching을 함께 센다. Left는 Receiver Right, Right는 Receiver Left이며 x는 .945/.055다. 정규화 높이는 먼저 유한값과 0~1 범위를 검사한다. 화면 표시에서는 각 기기의 실제 구슬 중심 이동 범위를 사용해 HUD·구슬·문구 여백 차이를 반영한다.

`AttackAuthority`의 기존 request 영수증 장부를 전달·발사가 공유한다. 상대 연결·sender·owner·round·OrbId·상태·sequence·보관 상한을 검증한다. 전달 승인은 물리 Projectile 생성을 요청하지 않는다. 중복 packet은 원 영수증을 돌려주며 owner 변경을 반복하지 않는다. T11의 Query는 기존 ID 확인 외에 원 요청의 방향·sequence·위치까지 비교한다. 기존 조회 API는 보존한다. 조합은 같은 Registry reservation으로 경합을 막는다.

`OrbRecord`와 `OrbWire`에 다음 이력을 보존한다.

| 값 | 의미 |
| --- | --- |
| `transferCount` | 같은 OrbId가 전달 승인된 횟수 |
| `lastTransferSequence` | 마지막 전달의 요청 sequence |
| `entrySide` | 마지막 수신 경계 |

발사·Projectile·Consumed 전이에도 이력은 유지하고, 조합으로 생긴 새 ID의 이력은0으로 시작한다. `GameWire`는 승인된 T11 context에서만 전달을 허용한다. 두 사람의 owner 변화는 전달 횟수 차이의 홀짝과 일치해야 한다. 일부 상태 갱신을 건너뛰어 A→B→A 또는 전달 직후 발사를 보더라도 검증할 수 있다. 이력 감소, 전달 없이 owner 변경, 사용 불가능한 상태에서 새 전달, terminal 변경을 거부한다. 논리 지문 V2에는 세 이력 필드를 포함하며 기존 숫자 오차 기준1e-6, 정수 정확성, nonce 제외는 유지한다. 과거 빌드15의 기록 지문을 새 알고리즘으로 덮어쓰지 않는다.

`AttackSession`은 영수증이 가리키는 inventory revision 이상의 Host 상태를 기다린다. 지연 영수증 전에 반환·발사·소모가 일어나도 최신 확정 상태로 해제한다. 전달 때문에 영구 삭제 표식을 붙이지 않는다. 응답 누락은 기존 요청 조회 후 확정되지 않으면 연결 종료이며 타임아웃 재생성은 없다.

`T09BattleController`는 새 전달 횟수일 때만 반대 경계 위치를 적용하고, 일반 상태 갱신에서는 같은 View 객체와 로컬 드래그 위치를 유지한다. 받은 구슬의 Host sequence를 다음 요청에 반영한다. 구슬 생성 영수증이 아직 Pending이면 T11 드래그를 잠가 생성 확인 전에 owner가 바뀌는 경합을 막는다. 송신 대기·성공/실패와 수신 경계 문구를 연결했고, 기존 잡기 확대·빛 효과를 유지한다.

## 검증 도구와 보존

새 EditMode 시험은 권한23, 영수증·wire12, snapshot16, 씬4, 제스처22로 총77개다. 기존837개를 포함한 실제 실행 수는914개다. 최종 XML과 실패·미실행 구분은 검증 문서를 따른다.

`T11TransferProbe`는 명시적인 개발 Mac 실행 인자가 있을 때만 작동한다. 정상 앱 시작과 iOS에서는 자동 조작하지 않는다. 실제 별도 Mac 두 프로세스에서17회 전달을 수행하며 조작은 자동 포인터다. 전달마다 양쪽 사전 상태를 확보하고, 진단 파일은 임시 파일 작성 후 원자적으로 공개한다. 영수증 누락·정상 wire의 중복 요청을 주입하고 Host 처리 로그까지 대조한다. 받은 Combined 명중 후에는 통합 상태의 HP80 반영까지 확인한 다음 최종 증거를 저장한다.

첫 두 회차의 기록·진단 실패는 보존했다. 첫 회차에서 빈 AssertionError를 성공으로 잘못 표시한 요약은 무효 기록으로 따로 보관했고, 공식 회차 상태를 FAIL로 정정했다. 현재 도구는 예외 유무로 실패를 판단하고 양쪽 결과를 모두 읽는다. 실제 플레이의 성공과 기록 비교 성공을 구분한다.

작업은 기존 Editor와 분리한 검증 복사본에서 수행했다. 원본1044개 파일의 작업 중 변경 유무를 확인한 뒤 필요한 소스·새 씬·문서·증거만 반영했다. 자동 생성된 Test Runner 임시 파일 및 렌더 파이프라인 설정 변화는 원본에 이관하지 않는다. 정확한 반영 목록과 해시는 `docs/evidence/T11/`에 남긴다. 기존 사용자 변경, 과거 증거, 원본Config·meta·씬은 보존하며 commit/push는 수행하지 않는다.
