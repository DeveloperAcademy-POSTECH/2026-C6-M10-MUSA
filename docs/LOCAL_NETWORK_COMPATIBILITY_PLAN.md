# 핫스팟·Wi-Fi 연결 호환성 개선 계획

작성일: 2026-09-15 · 상태: **L1 진단·핫스팟 데이터 왕복 확인 완료 / L2 이후 미시작**

L1의 실제 실행 결과와 진단 도구 사용법은 [L1 네트워크 진단 기록](L1_NETWORK_DIAGNOSTICS.md)을 따른다. 아래 실기기 게임 검증표는 L1의 데이터 왕복과 별도이며, 실행 증거 전에는 NOT_RUN을 유지한다.

## 1. 이번 결정과 목표

추가 패키지 없이 기존 NGO·Unity Transport·Bonjour를 보완한다. **iPhone이 핫스팟 제공자이자 게임 Host인 환경에서 iPad가 입장하고 함께 플레이하는 것**을 첫 실기기 목표로 삼는다. 일반 Wi-Fi의 주소 구성 차이에도 연결 성공률을 높이고, **인터넷 없는 동일 LAN 플레이를 유지**한다.

| 항목 | 결정 |
|---|---|
| 기본 구성 | Unity6000.5.7f1 / NGO2.13.1 / Transport6.5.0 / URP17.5.0 유지 |
| 추가 서비스·패키지 | Photon·Relay·외부 SDK·클라우드 계정 추가 없음. manifest/lock 변경 없음 |
| 구현 수단 | 기존 패키지의 공개 확장 API, C#, 필요한 범위의 Apple 공개 네트워크 API |
| 게임 규칙 | 2~5인·Host 최종 권한·Ready·구슬 물리/전달/조합·3D 피격·자원·180초·결과/Retry 유지 |
| 현재 승인 범위 | 후속 요청에 따라 L1 최소 진단 코드·빌드·실기기 전송 경로 확인을 수행. L2 이후는 자동 시작하지 않음 |

Photon 전환 검토와 온라인 Relay 추가안은 현재 실행 계획에서 제외한다. 별도 네트워크 서비스를 사용하지 않으므로 해당 서비스 이용료는 없으며, 인터넷 접속이나 클라우드 인증을 로비 진입 조건으로 만들지 않는다.

## 2. 기준과 기존 작업 상태

실제 대상은 조직 저장소 `2026-C6-M10-MUSA`의 Unity 프로젝트다. 계획 기준은 이관 커밋 `f05ffb4d7286c55db921cd3adc1f2c64299a5201`의 빌드24 파일이다. 현재 씬은 `Assets/_Project/HapioMVP/Scenes/ContinuousTransferBattle.unity`다. 이전 결과는 [공개 검증 요약](VALIDATION_SUMMARY.md)을 따른다.

| 확인 항목 | 현재 확인된 내용 |
|---|---|
| 기존 정상 환경 | 원본 기록에 일반 Wi-Fi의 iPhone+iPad 방 탐색·입장·연속 구슬 전달 성공이 있음 |
| 이번 핫스팟 실패 | iPhone Host+핫스팟, iPad에서 방은 보였으나 JOIN이 연결 완료 전 약8초에 시간 초과. 직접 IP 시도도 실패 |
| 주소 구성 | iPad 설정의 IPv4가 `/32`이고 여러 IPv6 주소도 존재. Client 자신의 IP나 라우터 표시를 Host 게임 주소로 바로 사용할 수 없었음 |
| 코드 제한 | Bonjour가 IPv4만 조회, 여러 주소 중 하나만 선택, Host는 IPv4 수신, 주소 변경 재시도 없음, 일반 오류 안내로 실패 단계가 가려짐 |
| 중단된 N1 초안 | 별도 임시 작업 폴더에 주소 후보·재시도·IPv4/IPv6 전송 관련 소스가 남아 있음. 일부 `.meta`·테스트 작성 전 중단한 미완성 코드 |
| N1 실행 증거 | Compile·EditMode·PlayMode·앱 빌드·서명·실기기 모두 **NOT_RUN**. 앱 빌드25는 초안의 예정 번호이며 배포 완료 번호가 아님 |

주소 계열 처리 문제가 유력하지만 아직 유일한 원인으로 확정하지 않는다. 자체 UDP 어댑터 채택도 확정하지 않으며, L1에서 기존 공개 API로 부족한 지점이 실증될 때만 구현 범위를 결정한다. 이전 일반 Wi-Fi 성공도 새 보완 코드의 성공을 대신하지 않는다. N1 초안을 통째로 병합하거나 이미 완료된 작업으로 계산하지 않는다.

## 3. 보완할 내용

### 주소 탐색과 실제 수신을 함께 개선

- Bonjour에서 IPv4(A)·IPv6(AAAA)를 함께 수집하고, 같은 방이 여러 인터페이스에서 발견돼도 유효한 주소 후보를 보존한다.
- 후보마다 주소·포트·인터페이스·만료를 관리한다. 중복 제거와 개수 제한을 적용하며, 한 주소 계열의 후보가 다른 계열을 전부 밀어내지 않도록 한다.
- IPv6 link-local 주소에는 어느 인터페이스로 보낼지 나타내는 **scope**를 보존한다. `%인터페이스번호`를 문자열에 붙이는 것만으로 UTP 내부까지 전달됐다고 가정하지 않는다.
- Host가 IPv4와 IPv6 Client를 모두 받을 수 있는지 실제 소켓으로 확인한다. `::` 하나로 수신 주소를 바꾸는 것만으로 두 계열을 지원했다고 판단하지 않는다.
- 설치된 공개 API로 먼저 검증한다. 부족한 부분에 한해 UTP의 사용자 정의 네트워크 인터페이스 확장 지점을 이용한 작은 어댑터를 둔다. 패키지 본체 수정·포크나 신뢰성 프로토콜 재작성은 하지 않는다.
- 저수준 주소 변환이 필요하면 한 파일에 격리하고, 설치 Unity/UTP 버전의 구조와 iOS IL2CPP 동작을 검증한다. 기존 NGO 순서 보장·재전송·분할 메시지 처리는 유지한다.

Apple도 IPv4에 고정된 앱과 기기 내 서버의 IPv6 호환성을 별도로 시험하도록 안내한다. Unity Transport6.5는 서로 다른 수신 경로를 함께 지원하는 구성과 확장 지점을 제공한다. 이 자료는 설계 근거이며 현재 앱의 핫스팟 성공 증거는 아니다. [Apple IPv6 안내](https://developer.apple.com/support/ipv6/) · [UTP6.5 수신 구성](https://docs.unity3d.com/Packages/com.unity.transport@6.5/manual/cross-play.html)

### 연결 시도·검색 수명 관리

- 한 번 누른 JOIN에 대해 후보를 순서대로 시도한다. room/build/nonce는 고정하고, 같은 사용자의 중복 좌석을 만들지 않는다.
- 연결 완료 전 응답 없음·경로 실패만 다음 후보로 넘긴다. 정원 초과·버전 불일치·이미 시작·중복 참가 같은 Host의 명시적 거부는 즉시 종료한다.
- 실패한 시도의 Shutdown과 콜백 정리가 끝난 뒤 다음 후보를 시작한다. 취소·화면 종료·실제 백그라운드 전환은 대기 중인 시도도 취소한다.
- 검색의 서비스 해석·주소 해석·메타데이터 수신에 제한 시간과 제한된 재시도를 둔다. 오래된 방·주소를 무한히 남기지 않고, 새 검색에 이전 오류가 다시 나타나지 않게 한다.
- 방을 종료한 뒤 네트워크가 바뀌면 새로 검색한다. 진행 중인 게임을 다른 네트워크로 자동 이전하거나 끊긴 게임 상태를 복원하는 기능은 이번 범위에 넣지 않는다.

현재 앱 제한8초와 전송 연결창8초, 승인 제한8초의 관계를 먼저 측정한다. N1의 후보당18초·전체60초·후보8개는 **검증 전 초안**이다. 실제 전송/승인 단계와 취소 반응을 확인해 최종 값을 한 곳에서 관리하고, 게임 중 단절·요청 검증 시간까지 일괄 늘리지 않는다. 특히 `GameSync/T10GameSession.cs`가 현재 연결용8초 상수를 참조하므로 접속 제한을 조정할 때 경기 응답 제한을 먼저 분리하고 기존 동작을 회귀 검사한다.

### 화면과 진단

- `검색 중 → 방 확인 → 연결 중 → Host 승인/초기 상태 확인 → 입장 완료`를 구분한다.
- 검색 실패, Host 무응답, 승인 거부, 입장 후 단절을 각각 안내한다. 권한 거부 증거 없이 권한 문제라고 단정하지 않는다.
- IPv6도 입력 가능한 Direct IP를 제공한다. 방 목록에서는 일반 사용자가 긴 주소를 해석할 필요 없이 JOIN할 수 있게 한다.
- 진단에는 빌드·시도 ID·주소 계열·후보 번호·단계·경과 시간·실패 코드를 남긴다. 상세 주소와 인터페이스는 필요한 로컬 진단에만 보관하고 공개 보고서는 일반화한다.
- 방 표시, 전송 연결, Host 승인, 최초 상태 수신을 별도 성공으로 기록한다. `Connected`만으로 게임 준비 완료를 판단하지 않는다.

## 4. 작업 순서와 통과 조건

각 단계는 검증 결과를 남긴 뒤 다음 단계로 진행한다. **첫 실기기 데이터 왕복을 확인하기 전에 로비·게임 전체에 수정 코드를 확산하지 않는다.**

| 단계 | 작업·산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| L1 진단·전송 경로 검증 | 기준/사용자 변경 보존, N1 초안 검토, 최소 진단 장면 또는 도구로 Host 수신·IPv4/IPv6·scope 확인 | Mac 양 주소 계열 시험 및 실제 iPhone 핫스팟↔iPad의 데이터 왕복 증거. 어느 경로가 성공했는지 기록 |
| L2 탐색·참가 통합 | 검증된 전송 경로를 연결하고 여러 후보·제한된 재시도·취소·검색 만료·단계별 안내 적용 | 후보 실패→다음 후보 성공, 명시적 거부 시 중단, 늦은 콜백 무시, 취소 후 재시작, 중복 좌석0. 최초 상태 확인까지 성공 |
| L3 게임·다인 회귀 | 기존 자동 검사, Mac 독립 앱의 IPv4/IPv6 혼합 3인·5인과 공통 상태 비교 | 소유권·자원·전달·조합·실제 피격·승패/Retry 회귀 통과. 패키지/Config의 무관한 변경0 |
| L4 실제 환경 확인 | 같은 수정 빌드로 아래 필수 환경 시험. 실패 단계·선택 경로·시간 기록 | 핫스팟·일반 Wi-Fi·인터넷 없는 LAN을 각각 검증. 미실행 환경은 NOT_RUN 유지 |
| L5 정리·인계 | 유지보수 설명·빌드 방법·검증 결과와 지원 환경 표 작성 | 공개 자료에 개인 주소·기기/서명 정보·원시 로그 없음. 실패/미실행과 재현 방법 명시 |

L1에서 핫스팟 왕복에 실패하면 Host 수신, 주소 해석, 인터페이스 범위, OS 권한, 네트워크 차단을 분리해 조사한다. 주소를 추측해 반복 입력하거나 대기 시간만 늘린 뒤 해결됐다고 기록하지 않는다. 추가 패키지가 필요하다는 결론이 나와도 자동 도입하지 않고 관찰 결과와 대안을 먼저 제시한다.

작업량은 **전송 경로와 iOS scope 확인이 가장 불확실하고**, 탐색·오류 UI는 비교적 범위가 명확하다. L1 결과로 구현 범위를 확정한 뒤 일정을 산정한다.

## 5. 실기기 검증표

아래는 앞으로 실행할 검사이며 현재 모두 **NOT_RUN**이다.

| 환경 | 확인할 내용 | 중요도 |
|---|---|---|
| iPhone 핫스팟+게임 Host → iPad Client | 방 발견·JOIN·최초 상태·양쪽 Ready·게임 시작. 이것이 최우선 실패 재현 환경 | 필수 |
| 일반 공유기 Wi-Fi | 같은 수정 빌드에서 양쪽 참가·플레이. 기존 IPv4 경로가 퇴행하지 않았는지 확인 | 필수 |
| 인터넷 없는 동일 LAN | 인터넷 uplink가 없는 준비된 LAN에서 새 방 생성부터 입장·플레이. 이전 연결을 유지한 것만으로 통과하지 않음 | 필수 |
| 동일 핫스팟에서 iPad Host → iPhone Client | Host 역할에 따라 특정 경로만 동작하는지 비교 | 권장 |
| 사용자가 실패했던 다른 Wi-Fi | 동일 증상을 재현하고 새 빌드와 비교. 사용 가능한 환경에서만 수행 | 확보 시 실행 |
| mDNS만 제한된 환경 | 방 자동 탐색 실패와 Direct IP 게임 통신 가능 여부 분리 | 통제 가능한 환경에서 실행 |
| 기기 간 통신 격리 환경 | 실제 정책이 확인될 때 제한을 기록하고 적절한 안내 확인 | 연결 성공 필수 조건이 아님 |

필수 환경에서는 **새 방 참가 → 짧은 플레이 → 종료 후 새 방 재입장**을 확인한다. 실제 터치는 양방향 전달과 직접 조합·투척 확인에 집중하고 반복 요청·동일 상태 대조는 자동화한다. 사람에게100회 조작을 요구하지 않는다. 대표 실기기 환경 한 곳에서는180초 한 판과 종료 상태도 관찰한다. 적은 반복의 성공은 회귀 확인이며 통계적인 연결 성공률을 입증한 것으로 표현하지 않는다.

네트워크마다 접속 시간과 승인/초기 상태 완료 시간을 기록한다. 약한 Wi-Fi는 같은 조건의 전후 비교와 설치 패키지의 기존 지연·손실 시험 기능을 이용해 확인한다. 실제 무선 시험과 인위적 손실 주입 결과를 구분하며, 재시도·취소·복구가 제한 없이 반복되지 않는지도 확인한다.

Mac은 자동 검사와3~5인 보조 참가에 사용한다. 실제 iPhone↔iPad 핫스팟 성공을 Mac 중계나 개발용 USB 통신으로 대신하지 않는다. 필요 시 최종 한 차례 케이블을 분리해 확인하고 로컬 기록은 다시 연결한 후 수집한다. Mac5앱 성공은 모바일5대 성공으로 기록하지 않는다.

| `Networking/`의 최소 전송 어댑터 | 공개 UTP 확장 API가 필요한 부분만 격리. 정확한 파일 구성은 L1에서 확정 |
| `Lobby/Discovery/` | A/AAAA 수집·주소 후보·인터페이스별 제거·검색 만료/재시도 |
| `Lobby/T10LobbySession.cs` | 후보 전달·Host 승인·최초 상태·오류 수명 연결 |
| `Lobby/T10LobbyController.cs`, `T10LobbyHud.cs` | 연결 진행·오류 안내·Direct IP 입력 |
| 관련 `Tests/`, `tools/` | 주소/수명 단위 검사, 실제 소켓·다인 실행 검증 |

Host 등록부·승인·송신자/소유자·중복/이전 요청 차단, 구슬 ID·속도·마찰, 자원 비용·회복, 실제3D 피격 및 전투 결과 규칙은 보존한다. 기존 씬·`.meta`·개인 수정·과거 검증 기록을 덮어쓰지 않는다. 씬/설정 연결은 필요한 경우에만 Unity Editor API로 수정한다.

새 앱 빌드 번호는 기존 설치본과 구별해 기록한다. 게임 메시지 계약을 바꾸지 않는다면 연결 개선 때문에 게임 프로토콜을 임의 변경하지 않고 앱 빌드 번호와 별도로 설명한다. 구 버전 혼합 지원을 완료 조건으로 추가하지 않으며, 시험은 양쪽 같은 새 빌드를 사용한다.

## 7. 지원 경계와 사람에게 필요한 작업

같은 Wi-Fi 이름이어도 Guest Network·AP/client isolation·방화벽이 **기기 간 데이터 통신 자체를 막으면**, 로컬 앱 수정만으로 해당 정책을 넘을 수 없다. 자동 탐색용 mDNS만 막힌 경우와 게임 UDP까지 막힌 경우를 구별한다. 시간 초과 하나만으로 차단을 확정하지 않는다. 네트워크 설정을 직접 바꾸거나 보안/개인정보 설정을 임의 해제하지 않는다.

현재 목표는 실제 사용 중인 핫스팟 문제 해결과 허용된 LAN의 호환성 향상이다. 모든 통신사·공유기·차단 정책에서의 성공이나 끊김 없는 네트워크 이동을 보장하는 계획은 아니다.

| 시점 | 사람에게 필요한 작업 |
|---|---|
| 계획 검토 | 이 범위로 다음 L1 작업을 요청 |
| L1·L4 실기기 시험 | iPhone·iPad 연결/잠금 해제, 같은 핫스팟 또는 Wi-Fi 선택, 실제 권한 알림에 응답 |
| 환경 전환 시험 | 일반 Wi-Fi와 인터넷 없는 테스트 LAN 준비. 사용 중인 공유기 설정 변경 없이 가능한 환경 우선 |
| 짧은 사용성 확인 | 방 입장·구슬 전달/투척·오류 안내가 보이는지 확인. 로그 수집과 반복 검사는 개발 측에서 진행 |

현재 계획 작성에 필요한 계정·유료 서비스 가입·새 패키지 설치는 없다. 기기와 특정 네트워크 환경은 구현 검증 단계에서만 필요하다.

## 8. 기록 규칙과 다음 작업

상태는 PASS/FAIL/NOT_RUN/BLOCKED로 기록한다. Compile, EditMode, PlayMode, Mac 다인, iOS Export, 서명 앱, 설치·실행, 실제 네트워크·Touch를 분리한다. 각 결과에는 실행 날짜·소스·앱 빌드·환경·기기 종류·검사 수·누락·근거를 남긴다. 원시 기기 로그와 상세 주소는 로컬에 보존하고 공개 문서에는 일반화한 결과만 넣는다.

**현재 승인된 L1 「핫스팟 진단·IPv4/IPv6 전송 경로 검증」의 필수 조건은 충족했다.** 다음으로 요청할 작업은 L2 「탐색·참가 통합」이다. L1 결과에 따라 확인된 수신 경로를 선택하며 N1 초안 전체를 자동 채택하지 않는다. 계획 승인 자체는 실행 완료 근거가 아니며, [L1 실제 검증 기록](L1_NETWORK_DIAGNOSTICS.md)을 기준으로 판단한다.
