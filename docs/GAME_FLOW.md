# 합이오 개발용 3요괴 게임 흐름 — #276

기존 `Assets/Lab/Scenes/Lab.unity`는 실험·회귀 검사용으로 유지한다. 새 게임은 `Assets/Hapio`에 별도 저장된 Scene·Canvas·영속 세션 Prefab을 사용한다. 아직 배포용 설정으로 전환하지 않았으며 기존 Lab 빌드 메뉴·앱 식별자·공유 설정 원본을 교체하지 않는다.

## 실행과 빌드

1. Unity에서 `Hapio > Open Home`을 선택하거나 `Assets/Hapio/Scenes/Home.unity`를 연다.
2. Play 후 기존 한지 타이틀의 **게임 시작**을 누르면 오프닝25컷·27페이지가 시작한다(#359 진입·#364 확대 컷). 완료·건너뛰기 후 추가 클릭 없이 방 목록을 연다. 앱 실행당 한 번만 재생하며 같은 실행의 Home 복귀에서는 반복하지 않는다. 방 목록에서 2~6명 칩으로 인원을 고르고 **새 방 만들기 +** → 모드를 고르면(기본 모드 3~5명, 땅따먹기 2·4·6명, #394) 광고 등록 완료 후 Host 로비에 자동 입장한다. 다른 참가자도 같은 게임의 방 카드를 눌러 입장한다. 기존 LAN·핫스팟·Direct IP 연결을 유지한다.
3. 로비에서 각자 고유한 P번호를 선택한다. 목표 인원·자리 선택·설정 확인이 완료되면 Host가 **요괴 봉인 시작 · 3스테이지**를 누른다.
4. 전환 중 준비 인원이 표시되고 전원 첫 상태 수신·화면 준비 후 `3 → 2 → 1 → 시작!`과 함께 전투가 시작된다(#306).
5. 일반 Story의 성공 결과는 실제 경기 기록을 넣은 봉인 카드 1회 → 후일담 → 마지막 컷을 유지한 결과 대기로 이어진다(#558/#566). 1·2스테이지는 전원 결과 수신·로컬 이야기 완료·관람 종료 뒤 Host가 **다음 스테이지**를 누른다. 3스테이지는 각자 **엔딩 보기**로 엔딩을 마친 뒤 Home으로 돌아간다. 자동 다음 스테이지·별도 Ready 입력은 없다. 시간 초과·전멸의 정상 패배는 실패 이야기·도달 봉인율을 표시하며 Host가 **이 스테이지 재도전**으로 같은 방·같은 스테이지를 다시 시작할 수 있다. 이탈·연결 끊김은 재도전 없이 Home만 제공한다. 세부 조건은 [스토리 결과 통합](STAGE_STORY_UI_INTEGRATION.md)을 따른다.

빠른 로컬 확인은 Home의 **DEV · SOLO** 버튼으로 가능하다. 일반 방은 기존 2~5명 연결 규칙을 사용하고, 땅따먹기 방만 2·4·6명이다(#394). 새 게임과 구형 Lab은 연결 승인 토큰이 다르므로 같은 방에서 섞어 사용할 수 없다. 새 로비 카드로 만든 게임의 실제 Bonjour 서비스 이름은 `Hapio-Room` 계열이고 화면에는 `수장고-N`으로 표시한다. 화면에서 쓰지 않는 기존 직접 `GameSession.Host()` API는 호환성을 위해 `Hapio-<8자리 GUID>` 이름을 유지한다. 서비스 종류는 공유하지만 TXT 규약을 Lab/Game별로 구분하므로 서로의 방은 검색 결과에서 제외한다. 직접 IP로 잘못된 종류나 구버전 방에 접속하면 최종 연결 승인에서 거절한다.

새 게임 빌드는 `Hapio > Development Build > Build Mac App / Export iOS Xcode Project`를 사용한다. 새 Scene 5개만 포함하고 Home이 첫 진입점이다. 결과물은 프로젝트의 `Builds/Hapio/<날짜-고유번호>/`에 생성하며 이전 결과물을 덮어쓰지 않는다. 항상 Development Build다. 기본 Build Settings는 기존 Lab 첫 항목을 유지하고 새 Scene을 뒤에 추가하므로 일반 Unity Build 버튼 대신 위 전용 메뉴를 사용한다. 이번 통합은 #262의 흐름을 계승하되 main의 기본 진입점이나 기존 Lab 파일 경로를 바꾸지 않는다.

## 타이틀·방 목록·모드 선택 UI (Figma 3905 / 4263 / 4268)

Home/Lobby의 공통 `GameLobby.prefab`을 사용한다. 타이틀은 기존 애니메이션 위에 293×56의 게임 시작 버튼을 둔다. 방 목록은 새 한지 크롭과 기존 구름 원본을 쓰며, 동지 수 2~6명 칩을 스크롤 없이 모두 표시한다. 열린 방은 348×84 카드와 15 간격의 세로 목록, 빈 목록은 별도 한지 패널로 전환한다. 직접 연결은 목록 아래 오른쪽에서 연다.

모드 선택은 345 너비의 둥근 카드다. 기본 모드 3~5명·땅따먹기 2/4/6명 규칙에 따라 버튼을 잠그고, 불가능한 모드의 사유를 두 버튼 아래 공통 위치에 표시한다. 두 모드가 가능한 4명 카드는 높이 266, 나머지는 292다. 개발용 솔로 버튼은 카드 밖에 유지한다. 한글은 기존 Shilla 폰트, 화살표·새로고침 기호는 Unity 기본 폰트를 사용한다.

어두운 막과 화면 끝 (#631): 메뉴는 402×874 기준 틀을 화면 안에 맞춰 키우므로 화면 비율이 기준과 다르면 틀 밖 좌우(또는 위아래)에 얇은 띠가 남는다. 모드 선택·직접 연결·크레딧의 어두운 막은 틀 안에 저장되어 있어, 실행 중에 `GameScreenEdgeCover`를 붙여 막이 그리는 모양만 화면 끝까지 늘린다. 막의 저장 크기, 막 안 창의 자리, 누를 수 있는 영역은 그대로다. 모드 선택 카드가 떠 있는 동안에는 바로 뒤의 **새 방 만들기 +** 버튼(카드보다 조금 넓어 둥근 끝이 비쳤다)을 숨기고, 카드가 닫히면 다시 보인다.

저장 에셋의 명시적 갱신은 기존 `Hapio > Upgrade 2v2 Lobby UI` 메뉴가 `GameMenuDesignUpgrade`를 함께 호출한다. Play/빌드에서 자동 재생성하지 않는다. 이 단계는 공통 메뉴 Prefab만 수정하며 오프닝·튜토리얼 진입과 자리 선택·연결 소유권은 기존 흐름을 따른다. 원본 출처와 크롭은 `Assets/Hapio/Art/UI/Source/README.md`를 참고한다.

## Scene의 책임

| Scene | 저장된 구성과 역할 |
| --- | --- |
| Home | 기존 타이틀 → 첫 게임 시작의 로컬 오프닝 → 방 목록, 방 생성·검색·Direct IP, 인원 조정, DEV 설정, 개발자 Solo |
| Lobby | 방 이름·참가자·P번호 선택, Host START, 로비 나가기, Host DEV 설정 |
| Battle | 기존 Lab 전투를 복사한 독립 Scene. **1~3스테이지 모두 같은 경로를 로드**한다. 전투 UI·카메라·구슬·박·일시정지·기존 DEV 조작을 재사용한다. |
| StageResult | Story: 실제 기록 봉인 카드·후일담·완성 박 관람·Host NEXT. 최종 카드에서 전체 기록·로컬 엔딩. Territory: 기존 단판 결과 |
| GameOver | 정상 Story 패배: 실패 이야기·실제 봉인율·Host 같은 스테이지 재도전. 이탈·연결 끊김·준비·로딩·동기화 실패: 불이/금옥이 이탈 화면과 나가기. 자동 복귀 없음 |

모든 새 메뉴의 Canvas·버튼·Text·슬라이더·입력·안전 영역은 저장된 GameObject다. `GameScreen`은 참조를 읽어 값과 버튼 동작만 연결한다. `GameSceneBuilder.CreateMissing`은 없는 에셋만 Unity API로 생성하며 이미 편집한 새 Scene을 재생성하지 않는다. 구형 Lab Scene은 저장하지 않는다.

#354의 `GameOpeningController`는 Home의 독립 `GameOpening.prefab`과 기존 StoryPlayer를 연결한다. #359부터 타이틀 게임 시작에서 재생하고, 오프닝 중 메뉴·DEV 입력을 막고 완료/스킵 시 입력 해제 뒤 방 목록을 연다. 게임 진행 상태는 Home을 유지하며 네트워크 상태를 추가하지 않는다. 에셋 편집·실패 복구·실행 내 재생 정책은 [앱 시작 오프닝](APP_START_OPENING.md)을 따른다.

Battle은 처음 만들 때만 저장된 Lab에서 복사했고(`CreateMissing`, Battle이 없을 때), 지금은 Lab에 없는 스테이지 배경(`GameStageBackgrounds`, #446/#447)·바닥·장식(#485/#487/#490)·주광(#515)을 가진 독립 Scene이다. 이후 Lab Scene 수정은 자동으로 전달되지 않으며, Lab 전체를 Battle 위에 다시 복사하는 도구는 없다(예전 `Hapio > Upgrade Existing Game Scenes From Current Lab`은 Battle 전용 구성을 지워서 제거했다). Lab 변경을 Battle에 옮길 때는 Battle을 직접 편집하거나 해당 객체만 고치는 대상 갱신을 쓴다. Home/Lobby에 저장된 DEV 행(0~256)은 `Hapio > Upgrade Menu DEV Rows`가 기존 객체와 배치를 유지하면서 원본에 맞추고, 257번부터는 실행 중에 붙는다(아래 에디터 도구 절). 일반 Play·빌드는 이 도구들을 자동 호출하지 않는다.

## 세션과 전투의 수명

`Resources/Hapio/GameSession.prefab`의 `GameSession`·`LabNetwork`·NGO·DualStackTransport가 방 연결과 진행 데이터를 유지한다. Scene 로딩은 NGO의 자동 Scene 전환 대신 Host가 승인한 작은 진행 메시지와 각 기기의 로컬 Scene 로드를 사용한다.

- `GameRunFlow`가 `runId`, `stageIndex`(1~3), 상태, revision, 종료 사유를 관리한다.
- 기존 전투의 `sessionId/round`는 별개다. 매 스테이지 새 전투 ID로 이전 판의 구슬·전달·투척 요청을 차단한다.
- `GameBattleBindings`가 새 Battle의 객체를 영속 Network에 연결한다. 이 연결은 기존 전투 초기화 코드보다 먼저 이뤄진다. Scene을 떠날 때 해당 참조·입력 구독·투사체를 정리한다.
- 전원 Battle 로딩·최신 설정·첫 상태와 화면 준비 확인 후 공통 카운트다운을 거쳐 Host가 전투를 시작한다. 이전 스테이지의 로딩 ACK는 다음 스테이지에 사용할 수 없다.
- 첫 스테이지 준비부터 홈 복귀 전까지 P번호 변경과 새 참가 승인을 잠근다. Scene 로딩 중 전투 모델이 잠시 없어도 이 잠금은 유지하며, 새 방에서는 해제한다.
- 각 기기는 실제 결과를 별도 복사하고 결과 Scene을 로드한 뒤 결과 수신 ACK를 보낸다. 성공 관람 사본은 완료 연출 중 확보한 캐시를 재사용한다. 정상 Story 패배도 정확한 Defeat 스냅샷을 기다리며, 이전 성공의 관람 사본을 실패 결과로 쓰지 않는다. Host NEXT·재도전은 로컬 이야기 완료와 관람 종료까지 기다린다. 최종 Host HOME은 기존 결과 수신 조건을 유지하며 다른 사람의 엔딩 종료까지 기다리지는 않는다.
- 전투 로딩에는 `GameSession.loadingTimeoutSeconds`(Prefab Inspector, 기본 30초)를 적용한다. Story의 완료·결과 사본 준비는 Host가 최초 Victory를 관측했을 때 시작한 공통 12초 한도를 공유하며, 결과 전환에서 30초를 새로 기다리지 않는다(#367). 한도가 끝나면 완료 연출을 생략하지만, 최종 지도 불일치가 남은 중간 `StageResult`는 기존 정책대로 GameOver가 된다. 최종 `Completed`만 클리어를 유지하고 지도 미동기화 안내와 함께 결과로 이동한다. CPU 지도가 일치해도 GPU 관람 사본 생성이 실패하면 별도 오류 안내 없이 관람이 비활성화될 수 있는 기존 제약은 남아 있다. 없는 도색을 만들어내지 않는다. 2:2의 실패 시 로비 복귀와 기존 같은 방 복귀 API는 유지하며, 현재 디자인 결과의 나가기는 연결 종료 후 타이틀로 복귀한다(#293/PR #382).

## 스테이지 경계

방 연결·참가자·고유 P번호·좌우 순서·승인된 설정은 유지한다. 매 스테이지는 새 모델로 제한시간·개인 HP·스태미나를 설정 시작값으로 복원하고 구슬·북 배치·투사체·도색·흔들림·콤보·방해 이벤트·통계를 초기화한다. 스테이지별 규칙·DEV 설정은 아래 카탈로그를 따른다. 누적 점수는 추가하지 않는다.

결과는 전투의 실제 종료 스냅샷을 별도 복사한다. 성공 기록만 스테이지별 전체 기록에 추가한다. 정상 Story 패배에서 Host가 재도전하면 이전 성공 기록·방·P번호·참가자·승인 설정은 유지하고 현재 시도만 새 전투 ID와 준비 장벽으로 다시 만든다. 재도전은 실패 시점의 원래 참가자가 모두 같은 방에 있고 결과/이야기를 확인한 때에만 가능하다. 완성 박은 완료 연출 중 기존 관람 복제 기능으로 텍스처·재질·렌더 카메라를 독립 보관하고 결과 전환에서 재사용한 뒤 Battle을 언로드한다. 누구든 관람 중이면 Host NEXT를 막고, 모두 닫은 뒤 Host가 직접 다음 스테이지를 시작한다. 다음 스테이지/홈 복귀 때 사본을 해제한다. Hapio Battle에서는 독립 Lab의 결과 카드·대시보드를 표시하지 않으며 공유 통계 계산과 관람 기능은 유지한다.

결과 화면은 활성화 즉시 내용을 초기화한다. 최소 다음 프레임을 지나고 모든 마우스·터치가 해제될 때까지 NEXT/HOME/관람 버튼과 해당 콜백을 차단해 전투 입력이 결과 행동으로 이어지지 않게 한다. 이후 새 입력으로 수동 진행하며 별도의 고정 초 대기는 없다.

## 종료·정지·DEV

- 진행 중(중간 결과 포함) 나가기, 참가자 이탈, Host 연결 상실 → 전원 게임 오버. Host 상실은 각 기기가 실제 연결 종료를 감지해 처리한다.
- 시간 초과·전원 개인 HP 0 → 일반 Story에서 재도전 가능한 GameOver(`retryableDefeat=true`). 실패 이야기와 실제 도달 봉인율을 표시하며 자동 재도전은 없다. Host 버튼으로 같은 스테이지만 다시 준비한다. 튜토리얼·Territory의 종료 처리는 기존 분기를 유지한다.
- 로비에서 나가기는 홈으로 복귀한다. 최종 클리어 뒤 정상 종료는 남아 있는 참가자의 클리어 결과를 게임 오버로 바꾸지 않는다.

## 전원 초기 동기화와 공통 카운트다운 (#306)

시작 버튼 → `LoadingBattle`(Scene·설정 준비) → `SynchronizingBattle`(초기 라운드 상태 반영) → `Countdown` → `Playing` 순서다. 새 상태는 기존 enum 번호 뒤에 추가한다. 첫 라운드·각 NEXT·DEV 같은 스테이지 재시작·솔로·2:2 시작이 같은 절차를 사용하며 Lab 단판은 기존 흐름을 유지한다.

- Host는 전원 Scene·설정 세대 확인 후 새 라운드를 초기화하되 `GameStartHeld`로 게임 시계·조합판/박 물리·모든 전투 입력을 고정한다. 사용자 Pause와 구분하므로 화면 UI·네트워크·공통 서버 시계는 계속 동작한다.
- 각 기기는 정확한 session/round의 snapshot·확정 도색·자기 owner-board checkpoint·실제 표시 객체·설정·카메라/HUD·박 표현을 확인한다. 표시 초기화에 한 프레임을 준 뒤 `initial_ready`를 보낸다. snapshot만 받은 상태는 완료가 아니다.
- 전원 완료 후 NGO `ServerTime.Time` 기준 미래 시각을 예약한다. 예약 수신 ACK가 모두 오면 작은 game-flow control의 `countdown_commit`으로 확정한다. 시작 시각은 밀리초로 정규화하고 ACK/확정의 식별은 판·설정·정수 revision으로 검증한다. JSON 왕복 소수점 값을 응답 식별자로 직접 비교하지 않는다. 숫자 표시 전에 예약이 확정되지 않으면 준비 화면을 유지하고 여유 시간을 늘려 다시 예약한다. 각 기기의 기동 시각이나 멈춘 전투 시계로 카운트다운하지 않는다.
- 공통 시작 시각의 3초 전부터 3/2/1, 해당 시각에 시작!을 표시한다. Host만 실제 판정 시계를 해제하고 참가자는 확정된 예약/Playing과 초기 상태가 맞을 때 조작을 연다. 시작! 표시는 0.5초 후 사라지며 그동안 터치를 가로막지 않는다.
- 시간 길이(3/2/1 3초, 첫 예약 여유 1초, 재예약 상한 5초, 시작! 0.5초)는 `GameSession.Start.cs`의 `GameStartTiming` 기본값이다. 게임 코드는 이 값을 바꾸지 않는다. `Hapio.PlayModeTests`만 `GameTestStartTiming`([SetUpFixture])으로 0.3초·0.1초·5초·0.1초로 줄였다가 끝나면 되돌린다. 순서·ACK·재예약·로드 한도는 같고 길이만 다르다. 카운트다운 자체를 보는 검사(`SharedCountdown…`)는 기본값으로 실행한다.
- Scene 로딩·초기 동기화·예약 확정까지 합쳐 기존 30초 한도를 적용하고 확정된 3초 표시는 별도로 마친다. 구세대·중복 ACK는 판/설정/revision으로 거부하며 재예약하면 이전 예약 ACK를 지운다. 실패·이탈은 기존 Story GameOver와 2:2 같은 방 로비 복귀 정책을 따른다.

연결은 `GameSession.Start.cs`(준비·예약·표시), `GameRunFlow`/`GameFlowSnapshot`(세대·전환 검증), `LabNetwork.GameFlow`(초기 상태·내부 hold·시계·해제), `GameBattleBindings.IsPresentationReady`, `GameStartOverlay`다. 현재 작업의 실행 결과와 미실행 환경은 `VALIDATION.md`의 #306 절에 기록한다.

## #311/#314 통합 기믹 정책

`LabModel.CastGimmicks`가 공용·고유의 단일 상위 발동 경로다. 일반 스테이지는 #311의 고정 주기·확률을 공급하고, 야광귀는 `LabModel.YaguangSchedule`의 예약 시각을 공급한다. 구형 별도 Timeline 엔진이나 폭탄/막기 개별 반복 타이머를 복원하지 않는다. 지귀 고유 패턴과2:2 무기믹 규칙은 유지한다.

야광귀 공용25/40/60/80초와 고유 예고10/35/60/75초를 Host 게임 시계로 순서대로 소비한다. 같은 시각에는 공용→고유, 고유끼리 같으면 콤보 우선이다. 공용과 고유는 겹치지만 고유끼리는 앞선 예고·효과·보상/페널티 종료 후 다음 예고 전체를 시작한다. 공용 대상이 없으면 그 occurrence는 건너뛰고 재예약하지 않는다. 두 공용 스위치 중 하나만 켜면 그 종류만, 둘 다 끄면 공용이 없다. 고유 스위치는 자기 종류의 slot만 제거하며 다른 종류로 대체하지 않는다.

- **구현:** `GameTouchInk`가 `GameSession` 아래에서 Scene을 넘어 유지된다. 입력은 장치(`Touchscreen`·`Mouse`)에서 직접 읽고, 캔버스에 `GraphicRaycaster`가 없어 버튼·스크롤 터치를 가로채지 않는다. 이 기기 화면에만 보이고 네트워크로 보내지 않는다.
- **그리는 순서:** Sorting Order 30050. 메뉴·오프닝 위, 장면 전환 페이드(30100)·로딩 화면(30150) 아래다.
- **모양:** 터치마다 가운데 얼룩의 종류·회전·크기와 주변 먹 방울의 개수·방향·거리·크기를 새로 정한다. 가운데 얼룩은 코드로 만든 둥근 먹 번짐 8종(`Art/UI/TouchInk/TouchInkBlob01~08`, [생성 기록](asset-generation/touch-ink-blobs.md))이고, 주변 방울은 `Resources/OrbBoard/Stains`의 튀김점 2종이다. 둘 다 먹색으로 칠해 쓴다.
- **사라지는 방식:** 찍히는 순간이 가장 진하고, 머무는 시간 없이 바로 옅어지며 살짝 번져 커진다.
- **소리:** 지금은 넣지 않았다. `TouchInkArt`의 `Tap Sound`에 소리를 넣으면 코드 수정 없이 터치할 때 한 번 난다(여러 손가락이 동시에 닿아도 한 번). Home 등에는 AudioListener가 없어서 소리가 나는 동안만 잠깐 붙이고, 게임의 효과음 크기 설정을 함께 따른다. 소리를 넣을 때는 [오디오 출처](AUDIO_CREDITS.md)에도 기록한다.
- **조절:** `Assets/Hapio/Resources/Hapio/UI/TouchInkArt.asset`의 Inspector 값이다. 터치 소리(`Tap Sound`)와 크기(`Sound Volume`), 희미한 정도(`Ink Strength`), 가운데 얼룩 크기(`Stain Size`), 사라지는 시간(`Fade Seconds`), 먹 방울 수(`Droplets Min/Max`)와 크기(`Droplet Size Min/Max`), 동시 표시 수(`Max Marks`). Play 중에 바꾸면 희미한 정도와 시간은 바로, 모양은 다음 터치부터 반영된다.
