# 합이오 개발용 3요괴 게임 흐름 — #276

기존 `Assets/Lab/Scenes/Lab.unity`는 실험·회귀 검사용으로 유지한다. 새 게임은 `Assets/Hapio`에 별도 저장된 Scene·Canvas·영속 세션 Prefab을 사용한다. 아직 배포용 설정으로 전환하지 않았으며 기존 Lab 빌드 메뉴·앱 식별자·공유 설정 원본을 교체하지 않는다.

## 실행과 빌드

1. Unity에서 `Hapio > Open Home`을 선택하거나 `Assets/Hapio/Scenes/Home.unity`를 연다.
2. Play 후 한지 타이틀의 **게임 시작**을 누른다. 방 목록에서 2~5명을 선택해 **새 방 만들기 +**를 누르면 광고 등록 완료 후 Host 로비에 자동 입장한다. 다른 참가자도 같은 게임의 방 카드를 눌러 입장한다. 기존 LAN·핫스팟·Direct IP 연결을 유지한다.
3. 로비에서 각자 고유한 P번호를 선택한다. 목표 인원·자리 선택·설정 확인이 완료되면 Host가 **요괴 봉인 시작 · 3스테이지**를 누른다.
4. 전환 중 준비 인원이 표시되고 전원 첫 상태 수신·화면 준비 후 `3 → 2 → 1 → 시작!`과 함께 전투가 시작된다(#306).
5. 1·2스테이지의 결과에서 Host가 NEXT를 눌러 전원이 다음 스테이지로 이동한다. 3스테이지 결과에서는 각자 HOME으로 돌아간다.

빠른 로컬 확인은 Home의 **DEV · SOLO** 버튼으로 가능하다. 일반 방은 기존 2~5명 연결 규칙을 사용한다. 새 게임과 구형 Lab은 연결 승인 토큰이 다르므로 같은 방에서 섞어 사용할 수 없다. 새 로비 카드로 만든 게임의 실제 Bonjour 서비스 이름은 `Hapio-Room` 계열이고 화면에는 `수장고-N`으로 표시한다. 화면에서 쓰지 않는 기존 직접 `GameSession.Host()` API는 호환성을 위해 `Hapio-<8자리 GUID>` 이름을 유지한다. 서비스 종류는 공유하지만 TXT 규약을 Lab/Game별로 구분하므로 서로의 방은 검색 결과에서 제외한다. 직접 IP로 잘못된 종류나 구버전 방에 접속하면 최종 연결 승인에서 거절한다.

새 게임 빌드는 `Hapio > Development Build > Build Mac App / Export iOS Xcode Project`를 사용한다. 새 Scene 5개만 포함하고 Home이 첫 진입점이다. 결과물은 프로젝트의 `Builds/Hapio/<날짜-고유번호>/`에 생성하며 이전 결과물을 덮어쓰지 않는다. 항상 Development Build다. 기본 Build Settings는 기존 Lab 첫 항목을 유지하고 새 Scene을 뒤에 추가하므로 일반 Unity Build 버튼 대신 위 전용 메뉴를 사용한다. 이번 통합은 #262의 흐름을 계승하되 main의 기본 진입점이나 기존 Lab 파일 경로를 바꾸지 않는다.

## Scene의 책임

| Scene | 저장된 구성과 역할 |
| --- | --- |
| Home | 방 생성·검색·Direct IP, 인원 조정, DEV 설정, 개발자 Solo |
| Lobby | 방 이름·참가자·P번호 선택, Host START, 로비 나가기, Host DEV 설정 |
| Battle | 기존 Lab 전투를 복사한 독립 Scene. **1~3스테이지 모두 같은 경로를 로드**한다. 전투 UI·카메라·구슬·박·일시정지·기존 DEV 조작을 재사용한다. |
| StageResult | 스테이지별 기록, 완성 박 관람, Host NEXT, 중도 QUIT RUN 또는 최종 HOME |
| GameOver | 종료 사유와 HOME. 자동으로 홈으로 사라지지 않는다. |

모든 새 메뉴의 Canvas·버튼·Text·슬라이더·입력·안전 영역은 저장된 GameObject다. `GameScreen`은 참조를 읽어 값과 버튼 동작만 연결한다. `GameSceneBuilder.CreateMissing`은 없는 에셋만 Unity API로 생성하며 이미 편집한 새 Scene을 재생성하지 않는다. 구형 Lab Scene은 저장하지 않는다.

이번 main 동기화에서는 최신 Lab의 3D 배경·미니맵 배치를 별도 Battle에 반영했다. Battle은 저장된 복사본이므로 이후 Lab Scene 수정이 자동으로 전달되지는 않는다. `Hapio > Upgrade Existing Game Scenes From Current Lab`은 명시적인 동기화 도구이며 Battle의 전투 구성을 다시 복사한다. Battle 전용 수정은 먼저 차이를 확인해 반영한다. 같은 도구의 Home/Lobby 설정 확장은 기존 객체와 배치를 유지하면서 새 DEV 행을 추가한다. 일반 Play·빌드는 이 도구를 자동 호출하지 않는다.

## 세션과 전투의 수명

`Resources/Hapio/GameSession.prefab`의 `GameSession`·`LabNetwork`·NGO·DualStackTransport가 방 연결과 진행 데이터를 유지한다. Scene 로딩은 NGO의 자동 Scene 전환 대신 Host가 승인한 작은 진행 메시지와 각 기기의 로컬 Scene 로드를 사용한다.

- `GameRunFlow`가 `runId`, `stageIndex`(1~3), 상태, revision, 종료 사유를 관리한다.
- 기존 전투의 `sessionId/round`는 별개다. 매 스테이지 새 전투 ID로 이전 판의 구슬·전달·투척 요청을 차단한다.
- `GameBattleBindings`가 새 Battle의 객체를 영속 Network에 연결한다. 이 연결은 기존 전투 초기화 코드보다 먼저 이뤄진다. Scene을 떠날 때 해당 참조·입력 구독·투사체를 정리한다.
- 전원 Battle 로딩·최신 설정·첫 상태와 화면 준비 확인 후 공통 카운트다운을 거쳐 Host가 전투를 시작한다. 이전 스테이지의 로딩 ACK는 다음 스테이지에 사용할 수 없다.
- 첫 스테이지 준비부터 홈 복귀 전까지 P번호 변경과 새 참가 승인을 잠근다. Scene 로딩 중 전투 모델이 잠시 없어도 이 잠금은 유지하며, 새 방에서는 해제한다.
- 결과도 각 기기가 실제 결과·완성 도색 사본을 보관하고 StageResult를 로드한 뒤 ACK한다. Host NEXT와 최종 HOME은 이 준비를 기다린다.
- 로딩/결과 동기화 대기 한도는 `GameSession.loadingTimeoutSeconds`(Prefab Inspector, 기본 30초)다. 중간 단계 동기화 실패는 게임 오버로 종료한다. 이미 확정된 최종 클리어는 유지하며 관람 사본을 확보하지 못했다는 안내와 함께 최종 결과로 이동한다. 없는 도색을 만들어내지 않는다.

## 스테이지 경계

방 연결·참가자·고유 P번호·좌우 순서·승인된 설정은 유지한다. 매 스테이지는 새 모델로 제한시간·개인 HP·스태미나를 설정 시작값으로 복원하고 구슬·북 배치·투사체·도색·흔들림·콤보·방해 이벤트·통계를 초기화한다. 스테이지별 규칙·DEV 설정은 아래 카탈로그를 따른다. 누적 점수는 추가하지 않는다.

결과는 전투의 실제 종료 스냅샷을 별도 복사한다. 완성 박은 기존 관람 복제 기능을 사용해 텍스처·재질·렌더 카메라를 독립 보관한 뒤 Battle을 언로드한다. 관람에서 돌아온 뒤 NEXT를 사용할 수 있고, Host가 NEXT를 누르면 다른 참가자의 관람도 닫힌다. 다음 스테이지/홈 복귀 때 사본을 해제한다.

## 종료·정지·DEV

- 진행 중(중간 결과 포함) 나가기, 참가자 이탈, Host 연결 상실 → 전원 게임 오버. Host 상실은 각 기기가 실제 연결 종료를 감지해 처리한다.
- 시간 초과·전원 개인 HP 0 → 즉시 게임 오버. 전투 패배 결과나 자동 Retry로 진행하지 않는다.
- 로비에서 나가기는 홈으로 복귀한다. 최종 클리어 뒤 정상 종료는 남아 있는 참가자의 클리어 결과를 게임 오버로 바꾸지 않는다.
- 게임 오버 상태와 종료 사유는 홈 입력까지 유지한다. 늦게 도착한 전투 스냅샷으로 다시 전투에 진입하지 않는다.
- 상태바/제어센터를 여는 동작 자체를 이탈로 추가하지 않는다. 기존 실제 백그라운드·연결 종료 동작은 별도다.
- 공동 일시정지와 Host 재개를 유지한다. 정지 메뉴의 QUIT RUN은 전원 게임 오버 경로다.
- Home/Lobby의 DEV 조정과 Battle의 기존 DEV를 사용한다. Host가 정지 중 설정을 적용하면 **현재 스테이지 번호를 유지**하고 새 Battle 인스턴스를 로드한다. 새 설정의 ACK와 전원 로딩 후 재시작한다.

## 변경 위치와 검증

새 코드: `Assets/Hapio/Scripts/Core/{GameSession,GameRunFlow,GameFlowState,GameFlowSnapshot,GameScenePaths}.cs`, `Scripts/UI`, `Editor/GameSceneBuilder.cs`, `Editor/GameBuild.cs`.

검사 코드는 `Assets/Hapio/Tests`와 `LabGameFlowBridgeTests`다. 현재 통합의 실제 실행 결과는 `VALIDATION.md`의 #278 절을 참조한다. Scene 흐름 검사의 승리 유도는 CPU 도색 완료용 fixture이며 실제 투척 명중을 검증했다고 해석하지 않는다. 기존 투척·도색 검사는 별도로 유지한다.

Home/Lobby DEV의 `공통 / 구미호 / 야광귀 / 지귀`에서 해당 값만 편집한다. 공통은 시간·개인HP·구슬·물리·도색·폭탄 무게·막기 시간 등 모든 스테이지에 공유한다. 전용 값은 해당 스테이지만 바뀐다. #311부터 공용 기믹 묶음의 간격·폭탄/막기 켜기·비율(205·207·208·169·170)은 공통이 아니라 **세 스테이지 탭 각각**에 있어 스테이지마다 따로 정한다. 기본값을 초기화할 때만 StageDefinition의 토글을 적용하며 매 NEXT/재시작마다 사용자 OFF를 다시 ON으로 덮지 않는다.

- 구미호: 고유 기믹 묶음(#311) 간격206, 여우불·매혹 켜기209/210과 비율171/172(합 100), 여우불·매혹 세부값173~177, 매혹 예고204. 구미호 스테이지는 언제나 이 묶음을 돌리므로 Lab 전용 `Lab Unique Gimmicks`(166)는 보이지 않는다. 은퇴한 87·88·152·154·167·168은 어느 탭에도 없다.
- 야광귀: 콤보155~164, 섬광184~190, 셈법191. 최초 기본값은 콤보·섬광·셈법 ON이다.
- 지귀: 수동 패턴178~183, 자동 간격192/193(기본20~30초), 소화/생성 화상 가중치194/195(기본1:1). 가중치0은 해당 자동 선택에서 제외하고 둘 다0이면 지귀 자동만 멈춘다. 공통 패턴은 계속된다.

새 Scene·카탈로그 생성/명시적 갱신은 `Hapio > Upgrade Three Yokai Stages`를 사용한다. 이 도구는 별도 Battle을 현재 저장 Lab에서 복사하므로 Battle 전용 수동 수정이 있다면 먼저 차이를 확인한다. 일반 Play/빌드에서는 자동 실행하지 않는다.

## 검증 상태

3요괴 흐름 #276과 새 로비 통합 #278의 실제 실행 결과는 `VALIDATION.md`의 각 기록을 따른다. #262·#270·#274의 과거 PASS는 새 3요괴 흐름의 검증으로 승계하지 않는다. 실제 iPhone/iPad·LAN·핫스팟은 수행하지 않았다면 NOT_RUN이다.


## #278 새 로비와 3스테이지 통합

- `Assets/Hapio/Art/UI/GameLobby.prefab`이 타이틀·방 목록·자리 선택·Direct IP·개발자 솔로 버튼의 공통 저장 UI다. Home/Lobby의 인스턴스가 각 Scene의 `GameScreen`을 참조한다. GameScreen은 기존 공통/구미호/야광귀/지귀 DEV 패널을 유지하고 `externalNavigation`일 때 구형 방/시작 버튼 입력을 연결하지 않는다. `GameLobbyView`는 표시와 입력만 처리하며 소켓·광고·전투 상태를 소유하지 않는다.
- `GameSession`이 시작부터 하나의 Game-family Network를 유지한다. 생성·카드 입장·검색·직접 IP·자리·시작·홈 동작은 이 세션을 통한다. 시작 버튼은 `StartGame`으로 연결되고 설정 ACK와 전원 로딩 ACK 후 기존 Battle을 시작한다. 시작을 이유로 연결을 다시 만들지 않는다.
- `GamePendingRoomRegistry`가 미입장 대기 방을 관리한다. 광고 준비 시에는 연결되지 않으며, Hapio의 실제 생성 버튼은 등록 완료 뒤 확정 광고를 같은 이름·포트로 자동 인계한다. 기존 별도 대기방 API는 명시적 카드 입장도 지원한다. 나머지 대기 방은 Home→Lobby→Battle→결과→Home을 거쳐 유지되며 GameSession 파괴/앱 종료 때 광고·예약 포트를 정리한다.
- 로비에서 나가면 방 목록으로 돌아간다. 최종 클리어 또는 게임 오버의 HOME은 타이틀로 돌아간다. 방 이름·Host와 P번호의 분리·2~5인·자리 선택 해제와 공유 설정(현재 200개) 확인 조건은 유지한다.
- Home/Lobby의 `Hapio UI Background Camera`는 3D 오브젝트를 그리지 않고 검은 배경만 지운다. Canvas는 Screen Space Overlay를 유지하며 Editor의 카메라 없음 안내를 방지한다.
- 위치 편집은 공통 Prefab에서 한다. `EditableSeatLayouts/Players2..5/P1..PN`이 각 인원의 저장된 자리 앵커이며 해당 앵커를 움직이면 자리 버튼 배치에 반영된다. 원본 Lab Scene의 UI 위치와는 독립적이다.
- 명시적 UI 적용 메뉴는 `Hapio/Upgrade Figma Game Lobby`다. 기존 공통 Prefab이 있으면 원본 Lab에서 재생성하지 않고 수동 편집을 보존한다. 이 작업은 Home/Lobby만 갱신하며 Battle·StageResult·GameOver를 복사하거나 저장하지 않는다. 일반 Play/빌드에서는 자동 재생성하지 않는다.
- 실험 단판은 계속 `Assets/Lab/Scenes/Lab.unity`에서 실행한다. 3스테이지 확인과 전용 빌드 진입점은 Home이다. 실제 실행 결과와 미검증 환경은 `VALIDATION.md`의 #278 절을 따른다.

## 전원 초기 동기화와 공통 카운트다운 (#306)

시작 버튼 → `LoadingBattle`(Scene·설정 준비) → `SynchronizingBattle`(초기 라운드 상태 반영) → `Countdown` → `Playing` 순서다. 새 상태는 기존 enum 번호 뒤에 추가한다. 첫 라운드·각 NEXT·DEV 같은 스테이지 재시작·솔로·2:2 시작이 같은 절차를 사용하며 Lab 단판은 기존 흐름을 유지한다.

- Host는 전원 Scene·설정 세대 확인 후 새 라운드를 초기화하되 `GameStartHeld`로 게임 시계·조합판/박 물리·모든 전투 입력을 고정한다. 사용자 Pause와 구분하므로 화면 UI·네트워크·공통 서버 시계는 계속 동작한다.
- 각 기기는 정확한 session/round의 snapshot·확정 도색·자기 owner-board checkpoint·실제 표시 객체·설정·카메라/HUD·박 표현을 확인한다. 표시 초기화에 한 프레임을 준 뒤 `initial_ready`를 보낸다. snapshot만 받은 상태는 완료가 아니다.
- 전원 완료 후 NGO `ServerTime.Time` 기준 미래 시각을 예약한다. 예약 수신 ACK가 모두 오면 작은 game-flow control의 `countdown_commit`으로 확정한다. 시작 시각은 밀리초로 정규화하고 ACK/확정의 식별은 판·설정·정수 revision으로 검증한다. JSON 왕복 소수점 값을 응답 식별자로 직접 비교하지 않는다. 숫자 표시 전에 예약이 확정되지 않으면 준비 화면을 유지하고 여유 시간을 늘려 다시 예약한다. 각 기기의 기동 시각이나 멈춘 전투 시계로 카운트다운하지 않는다.
- 공통 시작 시각의 3초 전부터 3/2/1, 해당 시각에 시작!을 표시한다. Host만 실제 판정 시계를 해제하고 참가자는 확정된 예약/Playing과 초기 상태가 맞을 때 조작을 연다. 시작! 표시는 0.5초 후 사라지며 그동안 터치를 가로막지 않는다.
- Scene 로딩·초기 동기화·예약 확정까지 합쳐 기존 30초 한도를 적용하고 확정된 3초 표시는 별도로 마친다. 구세대·중복 ACK는 판/설정/revision으로 거부하며 재예약하면 이전 예약 ACK를 지운다. 실패·이탈은 기존 Story GameOver와 2:2 같은 방 로비 복귀 정책을 따른다.
- 전환 UI는 `Resources/Hapio/GameStartOverlay.prefab`의 실제 Canvas·Background·SafeArea·Caption 객체다. 영속 GameSession이 소유하므로 Scene 언로드 중에도 남는다. 기존 Scene 배치를 다시 생성하지 않는다. `Hapio/Create Missing Battle Start Overlay`는 이 새 프리팹이 없을 때만 생성한다.

연결은 `GameSession.Start.cs`(준비·예약·표시), `GameRunFlow`/`GameFlowSnapshot`(세대·전환 검증), `LabNetwork.GameFlow`(초기 상태·내부 hold·시계·해제), `GameBattleBindings.IsPresentationReady`, `GameStartOverlay`다. 현재 작업의 실행 결과와 미실행 환경은 `VALIDATION.md`의 #306 절에 기록한다.

## #311/#314 통합 기믹 정책

`LabModel.CastGimmicks`가 공용·고유의 단일 상위 발동 경로다. 일반 스테이지는 #311의 고정 주기·확률을 공급하고, 야광귀는 `LabModel.YaguangSchedule`의 예약 시각을 공급한다. 구형 별도 Timeline 엔진이나 폭탄/막기 개별 반복 타이머를 복원하지 않는다. 지귀 고유 패턴과2:2 무기믹 규칙은 유지한다.

야광귀 공용25/40/60/80초와 고유 예고10/35/60/75초를 Host 게임 시계로 순서대로 소비한다. 같은 시각에는 공용→고유, 고유끼리 같으면 콤보 우선이다. 공용과 고유는 겹치지만 고유끼리는 앞선 예고·효과·보상/페널티 종료 후 다음 예고 전체를 시작한다. 공용 대상이 없으면 그 occurrence는 건너뛰고 재예약하지 않는다. 두 공용 스위치 중 하나만 켜면 그 종류만, 둘 다 끄면 공용이 없다. 고유 스위치는 자기 종류의 slot만 제거하며 다른 종류로 대체하지 않는다.

야광귀는 기본120초 전투·100초 방해 종료다. 종료 시각에는 같은 시각 콤보 timeout/폭탄 만료보다 먼저 남은 콤보를 무결과 취소하고 SMALL/BIG·섬광·넘기기 막기와 판 위 박 유래 폭탄을 정리한다. 비행 중인 공격이나 다른 출처의 구슬은 이 정리 대상이 아니다.100초 이후 새 기믹은 없고 전투는 계속된다. 값0은 종료 cutoff 없음 또는 해당 slot 없음이라는 각 필드의 뜻을 따른다. 승리/패배·Retry는 기존 세대와 clock 초기화를 따른다.

Hapio 설정211~224는 야광귀scope2 전용이다.205 공용간격,169/170 공용확률과 옛 고유 반복 시각은 야광귀에서 사용하지 않으므로 숨기고 변경을 거절한다. 공용 토글207/208·고유155/184는 유지한다. 일반 Lab None은 야광귀 전용 시간표를 실행하지 않는다. DEV79는 숨긴 고정0이다.
