## 0. 최신 후속 요구 — 좌우 경계를 넘어 이어지는 2D 물리

2026-09-14 실기기 확인 후 사용자가 원래 의도를 보완했다. **좌우 끝에 닿은 구슬은 튕기지 않고 이웃 화면으로 넘어가며, 물리 상태를 이어받아 마찰로 멈출 때까지 여러 화면을 계속 이동해야 한다.** 사용자가 이후 조정을 요청했으므로 이번에는 요구와 차이만 기록한다. 구현·빌드·새 검증은 진행하지 않았다.

### 후속 구현 기준

- 좌우 끝은 반발하는 벽이 아니라 원형 좌석의 이웃 화면으로 이어지는 통로다. 왼쪽으로 나가면 왼쪽 이웃의 오른쪽에, 오른쪽으로 나가면 오른쪽 이웃의 왼쪽에 이어진다.
- 손을 놓은 뒤 굴러가는 구슬도 경계에 도달하면 자동으로 넘어간다. 화면을 옮길 때마다 다시 드래그하거나 손을 놓는 입력을 요구하지 않는다.
- 넘어갈 때 속도 벡터·진행 방향 등 기존 물리 상태를 이어받는다. 경계를 통과했다는 이유로 멈추거나 반사되거나 속도가 추가되지 않는다. 마찰로 이미 줄어든 **남은 속도**가 다음 화면에서 계속 이어져야 한다.
- 한 화면을 지나 다음 화면의 끝에 닿으면 다시 그쪽 이웃으로 넘어간다. 같은 구슬 ID와 단일 소유권을 유지하며, 마찰로 충분히 느려져 정지할 때까지 연속 이동할 수 있어야 한다.
- Raw와 Combined의 좌우 이동에 적용한다. **자연 접촉만으로 조합하지 않는 규칙과 직접 드래그 조합은 유지**한다. 이번 변경은 좌우 경계에 대한 것이며, 상하 경계·구슬끼리의 반발과 정상 손떼기 3D 공격 규칙은 별도 변경 요청이 없는 한 기존 기준을 유지한다.

### 빌드23과 달라지는 부분

| 항목 | 현재 빌드23 | 후속 목표 |
|---|---|---|
| 관성 이동 중 좌우 끝 도달 | 벽 충돌·반발 | 해당 방향 이웃 화면으로 자동 통과 |
| 전달 입력 | 끝으로 직접 드래그한 뒤 정상 손떼기 | 굴러가는 구슬의 경계 도달로도 전달 |
| 수신 물리 | 반대쪽 빈 위치에 정지 수신 | 경계 전후의 물리 상태·남은 속도를 연결 |
| 여러 화면 이동 | 매 전달마다 새 직접 조작 필요 | 마찰로 멈출 때까지 입력 없이 연속 이동 |

이는 마찰 수치만 바꾸는 조정이 아니라 **경계 처리와 물리 상태의 네트워크 전달을 함께 바꾸는 작업**이다. 아래 기존 본문의 ‘정지 수신’, ‘벽 접촉 자동 전달 금지’, ‘소유권 변경 때 속도 정리’는 빌드23 구현 기준으로 보존한다. 후속 구현에서 이 절과 충돌하면 최신 요구인 이 절을 적용한다. 과거 P1/P3의 반발·정지 수신 PASS는 당시 동작의 증거이며 새 연속 이동의 PASS가 아니다.

### 착수할 때 정할 세부 사항

1. 서로 다른 화면 크기에서 높이와 속도를 이어주는 공통 물리 단위, 전달 시각, 지연 시간 동안의 마찰 계산. 경계에서 마찰을 중복 적용하거나 속도를 초기화하지 않도록 정한다.
2. 손으로 잡고 있는 구슬이 경계에 닿는 경우의 입력 처리. 자유롭게 굴러가는 구슬의 자동 통과 요구와 구분해 정한다.
3. 수신 측 보관 한도20개·진입 위치의 다른 구슬·전달 거절·연결 종료 시 동작. 실패했다고 구슬이 복제되거나 사라지지 않게 한다.
4. Host 승인과 소유권 변경, 승인 대기 중 표시, 전달 순서·중복 검사 및 메시지 버전. 현재 고정 회전을 새 회전 시스템으로 확대하는 등 별도 물리를 임의 추가하지 않는다.

### 후속 검증과 상태

2인 왕복과 3~5인 원형 연결에서 Raw/Combined가 좌우 경계를 넘어 여러 화면을 이동하다 마찰로 멈추는지 확인한다. 화면 경계에서의 반사·정지·가속, 중복 소유·유실, 자연 접촉에 의한 조합·오발이 없어야 한다. 서로 다른 기기 크기와 통신 지연 조건도 별도 확인한다.

**현재 상태: 요구 기록 완료 / 구현 대기 / 실행 검증 NOT_RUN.** 다음 구현 후보는 이 좌우 경계 연속 이동 하나다. 사용자의 후속 착수 요청 전에는 게임 코드나 빌드를 변경하지 않는다.

## 1. 목표와 진행 범위

기존 프로토타입 작업은 사용자의 판단에 따라 마무리한다. 다음 개발 범위는 세 가지다.

목적은 기본 기획을 동작하는 형태로 발전시키고, 사용자가 Unity에서 수치와 필요한 기능을 직접 커스텀할 수 있게 하는 것이다. 이 문서를 공통 계획·결정·진행 상태의 기준으로 사용한다. 구현 순서는 **공통 설계와 몬스터 규격 → 2D 물리 → 기준 표적 확인 → 3D 투척 → 최대 5인 통합**으로 진행한다.

2026-09-14 사용자가 기본 계획을 수용하고 몬스터 규격을 먼저 정의하는 방식을 승인했다. 최초 구현 범위는 P0 공통 준비와 P1 2D 물리였으며, 이후 별도 다음 요청으로 P2와 P3를 구현했다. 실행 범위별 상태는 아래 표와 검증 기록으로 구분한다. 이전 T14~T16과 과거 미실행 검증은 보존한다.

## 4. 공통 설계: 움직임과 게임 결과의 책임

### 개인 작업판은 소유 기기, 게임 결과는 Host

**계획상 선택:** 하단 2D 움직임은 해당 구슬을 가진 기기에서 계산한다. 생성·조합·전달·발사·소비·피해·자원·승패는 기존처럼 Host가 최종 승인한다. 실제 3D 발사체 물리도 Host가 계산하고 다른 기기는 승인된 비행 상태를 표시한다.

현재 자유 드래그도 위치를 매번 Host로 보내지 않고 각 기기의 로컬 표시 위치를 유지한다. 이 구조를 이어가면 개인 작업판 다섯 개의 연속 물리 동기화를 먼저 만들 필요가 없고 손가락 입력도 즉시 반영할 수 있다. 반면 이 선택은 모든 기기가 같은 2D 물리 좌표를 재현하거나, Host가 사람의 실제 터치를 입증한다는 뜻은 아니다.

현재 조합 Host 검사는 정규화 좌표의 유효성과 소유자·음양·상태·중복 요청 등을 확인한다. 실제 근접 거리는 소유 기기의 입력 코드가 판단하며 Host가 물리 장면을 재현해 검사하지 않는다. 새 구현에서도 이 책임 범위를 기록하고, 논리 상태 일치 시험과 로컬 움직임 시험을 분리한다.

### 먼저 맞출 계약

- **좌표:** 저장·통신 위치는 작업판 기준 정규화 좌표를 사용한다. 속도·거리·반지름 계산은 작업판 너비를 공통 기준으로 하되 세로 비율을 반영한다. 가로·세로를 각각 0~1로 만든 값을 그대로 원형 거리로 취급하지 않는다.
- **입력:** 잡기부터 정상 손떼기까지를 한 동작으로 묶는다. 취소·추가 손가락·UI에서 시작한 입력을 별도로 처리한다.
- **결과:** 한 손떼기는 `조합 / 좌우 전달 / 3D 투척 / 일반 2D 놓기` 중 하나만 실행한다.
- **소유권:** 일반 상태 갱신과 생성·전달로 인한 소유권 변경을 구분한다. 평범한 상태 수신이 굴러가는 구슬을 예전 위치로 되돌리지 않게 한다.
- **물리 상태 정리:** 소유권 변경·Retry·중단·화면 크기 변경 시 속도와 잡기·대기 상태를 정리하고, 드래그 중 바꾼 Body 유형·충돌 활성 여부를 정상값으로 복구한다. 승인 여부가 미확정인 구슬은 임의로 잠금을 풀지 않는다.
- **설정:** 기존 `ScreenLayoutConfig.asset`을 단일 원본으로 유지한다. 새 물리·투척 설정의 전달 범위와 검증을 추가하고, 실행용 사본을 사용한다.
- **통신:** 새 참가자 목록·투척 입력이 들어가는 메시지는 버전을 구분한다. 이전 빌드를 새 방에 섞어 잘못 해석하지 않게 한다.

## 5. 작업 A — 2D 구슬 물리

### 움직임

1. 화면 아래로 떨어지는 중력은 사용하지 않는다. 현재 하단 인터랙션 공간에서 원형 구슬끼리, 그리고 영역 경계와 충돌한다.
2. 일반 놓기에서는 최근 손 움직임으로 2D 초기 속도를 정한다. 빠르게 놓으면 더 빠르게 굴러가고, 천천히 놓으면 적게 움직인다.
3. 평면의 마찰감은 이동 속도를 줄이는 감속과 정지 기준으로 만든다. 벽·구슬 접촉의 마찰/반발과 평면에서의 지속 감속을 구분한다.
4. 미세한 떨림이 남지 않도록 충분히 느려지면 정지시킨다. 새 입력·다른 구슬의 충돌이 있으면 다시 움직일 수 있다.
5. 새로 생성하거나 전달받은 구슬은 유효한 빈 위치를 우선 사용한다. 겹친 채 생성되어 강하게 튀어나가는 상황을 방지한다.

기본 도구는 Unity의 Rigidbody2D와 Collider2D를 사용한다. 물리로 이동하는 중에는 기존 Transform 직접 이동과 동시에 위치를 쓰지 않도록 책임을 나눈다. 관련 개념: [Unity Dynamic Rigidbody2D](https://docs.unity3d.com/6000.0/Documentation/Manual/2d-physics/rigidbody/body-types/dynamic/dynamic-body-type-reference.html).

### 잡기와 직접 조합

- 잡으면 기존 관성 이동을 멈추고 손을 따라오게 한다. 기존 확대·빛 효과는 유지한다.
- 잡은 구슬이 다른 구슬을 계속 밀어내 조합을 방해하지 않도록, 잡는 동안 고체 충돌과 선택·조합 후보 감지를 분리한다. 다른 구슬 위에 직접 놓을 수 있어야 한다.
- 정상 손떼기 순간의 최근접 대상을 선택한다. 같은 음양을 놓았을 때 뒤에 있는 다른 음양으로 바꿔 합치지 않는다.
- 조합 요청 중에는 재료 두 개를 모두 잠근다. 성공하면 두 재료를 제거하고 새 Combined를 배치한다. 명확한 거절이면 겹침을 해소하고 물리 상태로 복귀한다.
- 잘못된 조합을 시도한 한 번의 손떼기를 좌우 전달로 다시 해석하지 않는다.
- **손을 놓은 뒤 굴러가다가 Yin과 Yang이 접촉해도 조합하지 않는다.** 벽 충돌로 전달·공격을 요청하지도 않는다.

Inspector에는 평면 감속, 정지 속도, 최대 이동 속도, 반발, 접촉 마찰을 노출한다. 명칭·초기 수치는 구현 단계에서 단위를 포함해 정하고 `DEMO_TUNING_VALUE`로 기록한다. 수치를 조절하기 위해 여러 코드 파일을 고칠 필요가 없게 한다.

## 6. 작업 B — 손떼기 3D 투척

### 선행 작업: 몬스터의 피격 규격

투척 감도를 정하기 전에 목표의 위치·크기·피격 범위·화면 구도를 기준값으로 고정한다. 모델 제작이나 이동 AI를 먼저 완성할 필요는 없다. [몬스터 표적 규격](MONSTER_TARGET_SPEC.md)에 기존 허수아비를 재사용한 기준값과 변경 절차를 기록한다.

- 정지한 표적 하나를 공통 3D 전장에 둔다. 기존 원점 위치, 중심 `(0, 1.4, 0)`, 크기 `(1.2, 2.6, 0.65)`의 BoxCollider를 초기 비교 기준으로 삼는다.
- 새 Prefab은 식별 루트·외형 Visual·피격 Hitbox를 분리한다. HP·피해를 Prefab에 중복 저장하지 않고 기존 Host 전투 상태를 사용한다.
- 외형만 교체해도 같은 판정 규격으로 비교할 수 있게 한다. 실제 목표 크기를 변경할 때에는 단일 Config를 고치고 표적을 다시 확인한 후 투척 감도를 맞춘다.
- 움직임·부위별 피해·약점·몬스터 공격·새 아트는 이번 기준 표적에 넣지 않는다. 이후 필요한 기능으로 독립 확장할 수 있다.
- P0/P1에서 기준 Prefab과 별도 씬을 먼저 연결한다. P2 시작 시 카메라에서 보이는 크기·명중 영역을 확인한 뒤 손떼기 입력과 탄도를 조정한다.

### 새 조작 흐름

**하단 Combined 잡기 → 상단 진입 시 투척 준비 → 정상 손떼기 → Host 승인 → 중력 비행 → 명중 또는 빗나감/만료.**

상단에 진입해도 손을 잡고 있는 동안에는 소비하거나 발사하지 않는다. 상단 준비 상태는 기존 잡기 효과와 함께 알아볼 수 있게 표시한다. 다시 하단으로 돌아오면 그 위치의 조합·전달·일반 놓기 규칙을 적용한다.

### 방향·세기와 피격

- 손떼기 직전의 짧은 입력 구간을 시간과 함께 기록한다. 전체 드래그 거리만으로 세기를 계산하지 않고, 화면 크기·프레임률·잡은 위치의 차이를 보정한다.
- 위로 던진 속도를 전방·상향 초기 속도로, 좌우 움직임을 좌우 방향으로 변환한다. 기존 고정 타깃 조준점으로 자동 보정하는 경로를 새 투척 경로에서 교체한다.
- 상단에서 멈춰 있다가 놓기, 작은 흔들림, 지나치게 큰 값, 유효하지 않은 시간·좌표를 처리한다. 정상 던지기 기준 미달이면 소비 없이 하단 유효 위치로 돌려보내는 것을 기본안으로 한다.
- Host가 발사 요청의 소유자·현재 상태·입력값 범위·중복 여부를 확인하고, 공유 Config로 실제 초기 속도를 계산한다. Client가 보내는 임의의 월드 속도를 그대로 적용하지 않는다.
- 중력을 사용하고 실제 Collider 충돌로 유효 명중을 확정한다. 표적은 기존 훈련 더미를 사용한다. 바닥 충돌·튕김은 피해를 만들지 않으며, 표적 유효 명중은 한 번만 처리한다.
- 명중 시 기존 피해20·공격자 회복5를 적용한다. 빗나감은 피해·명중 회복 없이 수명/영역 이탈 조건으로 정리한다.
- 다른 기기의 표시도 곡선 비행을 따라가도록 위치·속도·시간 정보와 보간을 점검한다. 각 Client가 별도로 피해를 계산하지 않는다.

Inspector 조절 항목은 투척 입력 수집 구간, 입력 감도, 최소·최대 초기 속도, 위/전방 변환 비율, 중력, 반발, 수명, 충돌 반지름이다. 입력 감도와 물리 속도의 단위를 구분하고, 첫 실제 조작에서 조정한 값을 기록한다. Unity의 중력 적용 속성은 [Rigidbody.useGravity](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Rigidbody-useGravity.html)를 참고한다.

### 손떼기 판단 순서

| 상황 | 실행할 동작 |
|---|---|
| 취소 입력, UI 시작, 이미 승인 대기, 전투 종료 | 새로운 조합·전달·투척 없음 |
| 직접 드래그한 Combined를 상단에서 유효한 던지기로 놓음 | 3D 투척 한 번 |
| Raw를 상단에 놓거나 투척 입력이 기준 미달 | 소비 없이 하단 복귀 |
| 하단에서 다른 구슬 위에 직접 놓음 | 조합 성공/거부 판단. 전달로 중복 처리하지 않음 |
| 하단에서 조합 대상 없이 좌우 전달 조건을 만족하며 놓음 | 해당 방향으로 전달 한 번 |
| 나머지 정상 하단 손떼기 | 초기 속도를 주고 2D 물리 이동 |
| 아무도 잡지 않은 구슬의 물리 접촉 | 충돌·반발만 적용 |

취소 후 늦게 들어오는 손떼기나 중복 응답도 두 번째 발사로 이어지지 않아야 한다. 승인 대기는 명확한 Host 결과나 새 라운드로 정리하며, 임의 시간 경과만으로 소비한 구슬을 복구하지 않는다.

## 7. 작업 C — 최대 5인 연결과 통합

### 참가자와 좌우 전달

P1이 Host이고 P2~P5가 참가한다. 기본안은 로비 입장 순서로 좌석을 정하고, 전투 시작 시 확정하는 원형 구조다. 예를 들어 3명이면 P1의 왼쪽은 P3, 오른쪽은 P2다. P1이 왼쪽으로 보낸 구슬은 P3 화면의 오른쪽에 도착한다. 2명에서는 양쪽 이웃이 동일한 기존 동작을 유지한다.

로비에서 나간 자리는 참가자 목록을 다시 정리하고 Ready를 재확인한다. 전투 중에는 순서를 바꾸거나 빈자리를 자동 대체하지 않는 것을 기본안으로 한다. Host만 시작할 수 있고, 6번째 참가자는 정원 초과로 거부한다.

### 확장할 부분

- `LobbyAuthority`의 단일 상대와 `LobbySnapshot`·`GameSnapshot`의 `p1/p2`를 목록으로 일반화한다.
- 참가자별 설정 수신 확인, Ready, 요청 순서, 응답 감시를 관리한다. 모든 승인된 Client에게 필요한 결과를 전달한다.
- 좌우 전달 수신자는 Host가 확정한 순서로 찾는다. 두 사람 사이 전달 횟수의 홀짝만으로 소유자를 추정하는 기존 검사를 교체한다.
- 구슬·자원·공격·시간·결과·Retry의 참가자 검사를 2~5명 기준으로 연결한다. 피해·회복은 실제 공격자에게 적용한다.
- 100개 보관 구슬과 추가 비행 상태를 포함한 전송 자료의 최악 크기를 측정한다. 수량·바이트 상한을 함께 정하고, 초과 자료는 무제한 허용하지 않는다. 필요한 경우 통신이 지원하는 분할 전송과 전송 빈도를 조정한다.
- 화면에는 전체 참가자, 내 순서와 좌우 이웃, Ready·입장 실패 이유를 보여 준다. 카메라 각도나 몬스터 난이도를 인원에 따라 자동 변경하지 않는다.

| P3 다인 통합 | 로비·좌우 순서·전달·상태 전송을 최대5인으로 확장 | 2·3·4·5인 연결과 3인 이상 생성→조합→전달→투척→결과 흐름 | 구현·자동·Mac2/3/4/5인·iOS빌드·실기기2대+Mac3인 기본동작/Bonjour PASS |

P0는 세 기능의 공통 준비이며 별도의 게임 기능을 늘리는 단계가 아니다. 물리 조작감을 작은 실행 환경에서 먼저 맞추고 마지막에 인원을 늘려 반복 빌드·기기 조작 비용을 줄인다.

구현은 기존 빌드20을 보존한 별도 개발 브랜치와 새 단계용 씬에서 진행하는 것을 기본안으로 한다. 공통 코드는 재사용하되 이전 씬이 새 손떼기 규칙이나 5인 메시지를 우연히 사용하지 않도록 적용 범위를 구분한다. 씬·참조·실행 절차를 함께 제공하며, 스크립트 파일만 만든 상태로 완료 처리하지 않는다.

## 9. 필요한 검증과 완료 조건

빌드23에서 P1/P2 물리를 포함한 기본 실기기 조작까지 확인했다. 이전 빌드의 개별 기기 NOT_RUN 기록은 소급해 바꾸지 않는다. 아래는 새 단계 전체의 검증 계획이다. 항목 전체를 이미 통과했다는 뜻이 아니며, 현재 실행한 범위는 [P1 검증](P1_VALIDATION.md)·[P2 검증](P2_VALIDATION.md)·[P3 검증](P3_VALIDATION.md)에 나눠 기록한다. 이전 1,037개 시험의 통과를 새 물리·다인 기능의 통과로 승계하지 않는다.

| ID | 확인할 동작 | 방법 / 통과 조건 |
|---|---|---|
| NP-01 | 2D 관성·감속·정지 | 같은 초기 속도에서 마찰 설정에 맞게 감속·정지. 지속 떨림·영역 탈출 없음 |
| NP-02 | 구슬·벽 충돌 | 겹침을 해소하고 밀림·반발. 정지한 구슬도 충돌을 받으면 이동 |
| NP-03 | 직접 조합만 허용 | 자연 접촉은 요청0건. 직접 Yin+Yang 드래그는 새 Combined1개, 같은 음양은 보존 |
| NP-04 | 잡기·놓기·취소 | 재잡기 가능, UI·추가 손가락·취소로 오발 없음. 한 손떼기에 행동 하나 |
| NP-05 | 투척 시점 | 상단에서 잡고 있을 때 발사0건, 유효한 정상 손떼기에서 발사1건 |
| NP-06 | 방향·세기·중력 | 좌우·느린/빠른 입력에 맞춰 궤적 변화. 같은 정상 입력의 프레임률·화면 차이는 합의한 허용 범위로 비교 |
| NP-07 | 실제 명중·소비 | 실제 충돌당 피해20·공격자+5 한 번. 빗나감·만료·중복 통지는 추가 피해/회복 없음 |
| NP-08 | 인원·Ready·정원 | 2·3·4·5인 각각 시작, 미Ready 시작 거부, 6번째 참가 거부 |
| NP-09 | 다인 좌우 전달 | 3인 이상에서 좌우가 서로 다른 이웃. Raw/Combined 양방향 전달, 반대편 도착·같은 ID·단일 소유자 |
| NP-10 | 공유 전투 | 참가자별 생성·조합·투척 후 같은 HP·시간·승패. 실제 공격자만 회복 |
| NP-11 | 취소·Retry·이탈 | 이전 요청·남은 속도·잠금·발사체가 다음 판에 영향 없음. 이탈 시 계획한 종료 정책 적용 |
| NP-12 | 수량·메시지 한도 | 5인×보관20 및 비행 상태의 실제 크기 확인. 자료 잘림·처리 불능·구슬 유실 없음 |
| NP-13 | 기기 조작감 | 실제 iPhone·iPad에서 굴림·조합·던지기와 확대 효과·Safe Area·버튼 확인 |

NP-06의 입력 샘플, 허용 오차와 NP-12의 비행 수·전송 상한은 해당 단계의 구현 전에 수치와 이유를 정해 기록한다. 자원을 주입해 부하를 만든 실행은 일반 플레이와 구분한다.

검증 환경은 다음처럼 나눈다.

- **Editor·자동 검사:** 감속·경계·직접 드래그 구분·취소·요청 중복·다인 좌석과 메시지 검사를 자동화한다. 로컬 물리 좌표를 모든 기기의 논리 상태 해시에 강제로 포함하지 않는다.
- **Mac 여러 실행본:** 3·4·5인 연결, 좌우 순서, 결과 일치와 메시지 크기를 먼저 확인한다. 실제 휴대기기 다섯 대 검증으로 기록하지 않는다.
- **보유 기기 통합:** iPhone+iPad+Mac을 사용할 수 있으면 3인 혼합 환경을 확인한다. 현재 연결 가능 여부는 실행 시 확인한다.
- **사람 확인:** 굴림·마찰·던지는 느낌처럼 코드만으로 판단할 수 없는 조작감을 짧게 모아 확인한다. 변경과 관련 없는 기존 반복 횟수를 기계적으로 다시 요구하지 않는다.

새 iOS 출력·앱 빌드·서명·설치·실행은 각각 결과를 기록한다. 실제 기기 다섯 대 확인이 필요해지면 별도 환경 항목으로 남기며, 그 장비가 없다는 이유로 계획서나 가능한 자동·3인 혼합 시험을 중단하지 않는다.

## 10. 기록·보존과 다음 시작점

계획은 이 파일에서 관리하고 각 단계 종료 시 아래 표를 갱신한다. 상세 실행 증거가 필요하면 기존 `docs/evidence/` 규칙을 사용한다. 설정값·변경 이유·코드 커밋·실제 빌드·기기·입력 방식·결과를 연결하고, 원시 로그·앱·서명 자료는 기존 Git 제외 규칙을 따른다.

| 기록 대상 | 현재 상태 |
|---|---|
| 새 요구사항 정리·코드 영향 조사 | 문서에 반영 완료 |
| 2D·3D 조작 규칙 | 사용자 확정 내용과 기본 제안을 2장에 구분 |
| 새 코드·씬·Config 변경 | P0/P1 PhysicsBattle을 보존하고 P2 ThrowBattle·손떼기·중력·표적 구도 연결 |
| 새 시험·빌드·실기기 결과 | [P3 실기기 후속](P3_DEVICE_VALIDATION.md)에서 현재 실행과 미실행을 구분 |
| 현재 구현 / 후속 후보 | **P3까지 세 기능 구현 및 iPhone+iPad+Mac3인 기본조작 확인** / 후속 후보는 좌우 경계 자동 통과·물리 상태를 유지하는 연속 이동(구현 대기) |

현재 각 단계의 사용자 후속 요청으로 P3까지 구현했다. 마찰·반발은 실제 실행에서 조정 가능한 초깃값으로 기록한다. 별도 확정이 필요한 플레이 규칙이 생기면 관련 내용만 모아 확인한다.
