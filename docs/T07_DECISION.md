# T07 · 개인 Stamina·생성·회복 결정

이 문서는 최신 사용자 변경과 T07 구현 계약을 기록한다. 시험·빌드·기기 실행 결과는 [VALIDATION.md](VALIDATION.md)에 실제 증거로 기입한다. 문서 승인이나 아래 예상 동작은 실행 결과가 아니다.

## 최신 사용자 변경의 적용

사용자는 “최초 5개”를 가득 찬 최대 5단계 게이지로 해석하도록 정정했고, 시작할 때 생성되어 있는 구슬도 없다고 명시했다. 후속 수치 지시는 최대/시작 100, 생성 비용 20, 3초당 20 자동 회복, 유효 피격 보너스 5다.

| 종전 통합본 | T07 채택 규칙 |
|---|---|
| 첫 Tap Raw 5개 / 비용 5 | 모든 Generate가 Raw 1개 / 비용 20 |
| 최초 생성 완료 플래그 | 별도 최초 묶음과 플래그 없음 |
| Stamina 최대/시작 5 | 최대/시작 100, 화면을 20 단위 다섯 구간으로 표시 |
| 시간 자동 회복 금지 | Playing 동안 Host 시간으로 연속 회복 |
| 유효 피격의 공격자 +1 | 실제 유효 피격의 공격자 +5 |

최신 사용자 지시가 원문 T07 및 공통 규칙의 충돌 부분보다 우선한다. 통합본·과거 Task 기록을 고쳐 과거 결과까지 바꾸지 않는다. 같은 취지의 미러 안내도 실제 T07에서 변경된 규칙을 되돌리는 근거로 사용하지 않는다.

## 자원 모델과 회복 시계

원본 설정은 기존 `ScreenLayoutConfig.asset` 하나다. 자원 모델은 플레이어별 연속 double 값을 사용하며 화면 구분선이 내부 값을 양자화하지 않는다. `3초당 20`을 `경과초 × (20 / 3)`의 연속 회복으로 구현하는 것은 **DEMO_ASSUMPTION**이다. 별도 타이머마다 20을 일괄 지급하지 않는다.

실제 NGO Host 서비스만 단조 증가하는 `Time.realtimeSinceStartupAsDouble`을 자원 권한 객체에 제공한다. 회복 조건은 현재 Playing이며 운영체제의 앱 일시 정지 상태가 아닌 경우다. `OnApplicationPause`로 Host 회복을 멈추고 복귀할 때 백그라운드 경과 시간을 지급하지 않는다. 단순 창 포커스 상실은 일시 정지로 취급하지 않아 Mac의 별도 Host/Client 실행을 유지한다. 클라이언트의 경과 시간·자원 수치·음양 선택은 받지 않는다. 이전 상태의 마지막 시점부터 현재 시점까지 먼저 정산한 뒤 Playing 여부를 전환하므로, 멈춘 구간이 재개 순간의 회복으로 누적되지 않는다. 최대값에서 넘친 분량은 버리고, 다음 소비 뒤 그 시간을 다시 지급하지 않는다.

일반 라운드는 빈 Host 구슬 Registry를 요구한다. Host·인증된 Client에게 각 100을 주며 구슬은 생성하지 않는다. 참가자가 늦게 들어와도 그 사람의 자원과 빈 개인 보관함을 별도로 시작한다. T09의 정식 Ready/Playing·승패·Reset은 아직 구현하지 않고 T06의 명시적 개발 Playing 상태에 연결한다.

## 생성 승인과 Seed

Generate 요청은 sessionId·roundId·requestId·sequence 및 연산 종류를 보낸다. 실제 송신자 ID와 세션 nonce는 NGO 연결에서 검증한다. 요청에 임의 소유자·자원·음양을 넣어 확정할 수 없다.

Host는 현재 라운드·참가자·Playing·신규 sequence·Stamina·개인 보관 상한을 검사한다. 성공하면 새 Raw ID 등록을 확정한 뒤 비용 20을 차감하고 그 플레이어의 성공 생성 순번을 1 늘린다. 구슬 추가와 비용 차감이 분리된 부분 성공을 만들지 않는다. 시작이나 첫 요청에 특별한 5개 경로는 없다.

보관 수는 같은 소유자의 Idle과 Launching이다. Projectile·Consumed는 제외한다. 신규 위치는 중앙 설정의 상한에 대응하는 격자에서 비어 있는 첫 칸을 고르며, 기본 상한 20은 5열×4행이다. 클라이언트 화면은 그 정규화 위치를 실제 하단 작업 공간에 표시한다. 실제 전달은 후속 Task지만 이미 소유한 구슬도 상한 계산에서 빠지지 않는다.

일반 Seed는 새 Host 세션에서 정하고 로그·snapshot에 기록한다. 같은 세션의 Reset은 Seed를 유지하고 성공 순번을 다시 0부터 시작하므로 같은 플레이어의 생성 순서를 재현할 수 있다. Seed·실제 플레이어 ID·성공 순번에 SplitMix64 방식의 카운터 혼합을 적용하고 한 비트로 Yin/Yang을 고른다. 이것은 **DEMO_ASSUMPTION**이며 보안용 난수나 짧은 구간의 50:50 개수 보장이 아니다.

거절·동일 중복 요청은 성공 순번을 늘리지 않고 난수 결과를 소모하지 않는다. 다른 플레이어의 요청 순서도 내 생성 순서를 바꾸지 않는다. 처음 본 유효 sequence는 거절되더라도 퇴역시켜, 오래된 명령이 나중에 회복된 자원으로 실행되는 것을 막는다. 거절 시 생성 비용과 구슬 상태는 유지하지만, 독립적인 정상 시간 회복까지 되돌리지는 않는다. 부동소수점의 정확한 비용 경계에는 비용 크기에 비례한 작은 허용 오차를 사용하고 차감 후 음수는 0으로 제한한다.

## 중복·조회·네트워크 경계

동일 requestId와 동일 요청 내용·소유자는 기존 영수증을 돌려준다. 같은 ID를 다른 sequence·연산·송신자로 재사용하면 거절한다. 현재 session/round와 맞지 않는 오래된 메시지는 현재 상태를 변경하지 않는다. 라운드별·참가자별 신규 자원 요청은 최대 256개로 제한한다.

클라이언트는 Generate 한 건을 대기 상태로 관리한다. 3초가 지나면 Host 영수증을 조회하며 동일 생성을 다시 보내지 않는다. 8초까지 확인되지 않으면 세션을 NetworkError로 종료한다. 로컬 타임아웃으로 구슬을 만들거나 비용을 복원·차감하지 않는다. 새 라운드는 기존 요청·영수증·입력·대기를 분리한다.

T07 자원 패킷은 버전·길이·UTF-8 JSON을 가진 최대 8 KiB 데이터다. Host 발신·nonce·현재 session/round·증가하는 revision·필드 범위를 확인한 snapshot만 표시한다. 기본 20 Hz 간격은 단일 Config의 `AttackSnapshotRateHz`를 재사용한다. 화면은 확인된 Host 값만 사용하고 자체 회복을 예측 계산하지 않는다.

T06 공격 서비스의 기본 Fixture/패킷 제한은 기존 씬에서 유지한다. T07 Controller만 연결 시작 전에 `ConfigureInventory(false, 64)`를 호출하여 자동 Fixture를 끄고 공격 snapshot을 최대 살아 있는 구슬 64개·32 KiB로 확장한다. T07 snapshot에서는 Consumed 이력을 제외하되 Host Registry·영수증의 종료 이력은 유지한다. 이 제한은 개인 보관 상한 20과 별개인 전송 상한이다. 이를 전체 게임 상태 동기화 T10-B의 완료로 해석하지 않는다.

## 실제 피격 보너스와 마지막 타격 순서

T06의 실제 Host Rigidbody/Collider 충돌 결과만 `ValidHit`에 들어간다. HP와 Consumed·누적 hit·잔여 투사체 정리·공격 snapshot을 먼저 확정한 뒤, T07이 같은 결과의 공격자·OrbId·session/round를 검사한다. 임의 클라이언트 메시지나 Collider 없는 표시 구체는 보너스를 발생시키지 못한다.

HP를 0으로 만든 유효한 마지막 타격도 보너스를 받는다. 공격 서비스가 먼저 TargetCleared를 게시하더라도, 그 피격은 이미 성공한 현재 라운드의 결과이므로 자원 라운드가 Ended가 되기 전 한 번 처리한다. 이때 시간 회복은 더 진행하지 않으며 이후 생성·발사도 허용하지 않는다. 종료된 라운드나 다른 라운드의 hit를 나중에 보상하지 않는다.

보상한 OrbId를 기록한 뒤 공격자에게만 최대 5를 더하고 100으로 제한한다. 이미 최대값이면 유효 피격이어도 실제 추가량은 0이다. 빗나감·만료·실패·중복 알림은 보너스를 만들지 않는다. 다른 플레이어는 자신의 정상 시간 회복만 계속할 수 있다. 화면의 전후 차이는 비행 중 시간 회복과 합산될 수 있으므로, 정확한 피격 보너스는 `C6_T07_HIT_RECOVERY`의 before/after/added와 실제 hit ID로 판정한다.

## Debug 도구·표시·보존

`DEBUG FIXTURE`는 Host의 명시적 새 라운드 요청이다. `ResourceDebugToolsEnabled`와 Editor/Development Build 조건을 만족해야 하고 P1 Yin 5개/P2 Yang 5개를 공급한다. 일반 Seed 생성·비용 20 시험과 결과를 섞지 않는다. 별도 `DEV HIT ORB` 요청은 Debug 모드에서 실제 공격·보너스를 시험하기 위한 무료 Combined 1개다. 조합을 구현하거나 성공했다고 기록하는 경로가 아니다.

새 `T07Hud`, `T07ResourceController`, `ResourceSmokeBuild`를 사용하여 기존 T06 씬·HUD·Controller를 보존한다. 공통 Host Registry·공격 서비스·단일 Config의 필요한 확장만 반영하고 기존 기본값 경로의 회귀를 확인한다. UI의 5×4 배치는 20개를 수용하기 위한 표시 선택이며 작은 화면의 라벨·터치·Safe Area는 실제 렌더와 기기로 확인한다.

컴파일·EditMode·PlayMode·Mac 렌더·Host/Client·iOS export·서명·설치·실기기 입력은 각각 증거가 필요하다. 합성 입력과 Debug 공급을 일반 생성이나 실물 손가락 조작으로 기록하지 않는다. T07 뒤 후보는 T08의 1단계 음양 조합 하나이며, 정식 Core Loop의 G4 실기기 Gate는 T09에서 수행한다.
