# P3 최대 5인 연결 · 구현 결정

2026-09-14 사용자 다음 작업 요청에 따라 P3 하나를 진행한다. 기존 빌드22와 원본 Editor를 보존하고 별도 작업 폴더에서 빌드23 `FivePlayerBattle`을 만든다.

## 구현 전 수량·통신 상한

- 방 정원 5명, 게임 시작 최소 2명. 입장 순서의 원형 좌석을 시작 때 고정한다. P1 왼쪽은 마지막 참가자, 오른쪽은 P2다. 로비 이탈 시 좌석을 정리하고 Ready를 다시 받는다. 전투 이탈 시 기존 종료 정책을 적용한다.
- 개인 보관 20개 × 5명 = 100개. 비행은 별도 개인 20개 × 5명 = 100개를 상한으로 정한다. 발사 승인 전에 검사하며 초과 구슬은 하단에 남는다. **DEMO_TUNING_VALUE:** 비행 상한은 전송 크기와 물리 비용을 유한하게 만드는 개발 기준이며 보관 제한이나 생성 비용을 바꾸지 않는다.
- 동시에 살아 있는 구슬 레코드 최대 200개, 실제 비행 정보 최대 100개. 종료된 레코드는 Host 영수증/중복 검사에 남고 전송할 활성 목록에서는 빠진다.
- P3 Attack 메시지 최대 262,144바이트, 전체 Game 메시지 최대 327,680바이트. 최대 길이 ID를 포함한 직렬화 검사와 실제 여러 Mac 실행본의 전송 결과를 따로 기록한다. 실행 전에는 PASS로 판단하지 않는다.
- 설치된 NGO 2.13.1 소스에서 ReliableFragmentedSequenced가 reliable stream을 사용하며 MaxPayloadSize 검사는 unreliable에만 적용함을 확인했다. 현재 reliable 전송 큐는 320 KiB보다 크므로 먼저 기존 분할 전송으로 검사하고 결과가 요구할 때만 조절한다. [공식 전송 방식](https://docs.unity.cn/Packages/com.unity.netcode.gameobjects%402.13/api/Unity.Netcode.NetworkDelivery.html). 패키지를 교체하지 않는다.
- 전달 횟수와 누적 오른쪽 전달 횟수를 보관한다. 건너뛴 상태 사이에도 오른쪽−왼쪽 순 이동량으로 원형 좌석의 최종 소유자를 검증한다. 동일 ID·반대쪽 도착·정지 수신을 유지한다.

## 보존과 검증 범위

구형 씬은 기본 2인 프로토콜을 유지한다. 2D 물리, 직접 손떼기 조합, 손떼기 3D 투척, 피해20·공격자회복5·시작0개·스태미나100·생성20·시간 회복20/3초는 유지한다. 카메라와 몬스터 난이도를 참가자 수에 따라 바꾸지 않는다.

새 Mac 진단은 명시적 실행 인자에서만 켜진다. 정상 유료 Generate와 특정 극성/Combined/최대 수량을 만드는 개발 주입을 분리해서 기록한다. 자동 포인터는 실제 Touch가 아니다. iOS 설치·실행·실제 기기 확인은 각각 별도 결과로 기록한다.

## 전달 방향을 별도로 세는 이유

2명일 때는 전달 횟수의 홀짝만으로 원래 소유자와 상대를 구분할 수 있었다. 3명부터는 같은 한 번의 전달도 왼쪽인지 오른쪽인지에 따라 받는 사람이 달라진다. 그래서 전체 `transferCount`와 누적 오른쪽 `rightTransferCount`를 함께 기록한다. 왼쪽 누적 횟수는 두 값의 차이다.

Client가 중간 상태 몇 개를 건너뛰어 받더라도, 이전 상태 이후 오른쪽 횟수와 왼쪽 횟수의 차이를 좌석 수로 나눈 나머지로 예상 소유자를 구할 수 있다. 예를 들어3명에서 P1이 오른쪽으로2번 이동하면 P3이고, 오른쪽1번 뒤 왼쪽1번이면 다시 P1이다. 횟수가 줄거나, 마지막 도착 방향과 맞지 않거나, 계산한 소유자와 다른 상태는 거부한다. 이 계산은 Host의 매 전달 소유자·방향 검사를 대체하지 않고, 받은 연속 상태를 추가로 확인하는 역할이다.

## 참가자마다 확인 응답을 관리하는 이유

2인 구조의 단일 응답 시각을5인에서 공유하면 P2가 계속 응답한다는 이유로 응답 없는 P5까지 정상으로 오인할 수 있다. `ParticipantGameBarrier`는 원격 참가자 ID마다 초기 확인 여부와 마지막 유효 응답 시각을 보관한다. Host는 모든 Client의 초기 상태 확인을 받아야 게임 조작을 열며, 한 사람의 응답으로 다른 사람의 확인을 대신하지 않는다. 응답은 먼저 방·세션·라운드·참가자·일회성 연결 식별자·상태 지문을 검증한 뒤 반영한다.

Retry는 새 라운드의 확인을 다시 받고, 연결 종료는 기존 확인과 요청·입력 상태를 정리한다. 로비에서 나간 사람이 다시 들어오면 마지막 자리에 배치되고, 전투 중에는 고정된 참가자 명단을 바꾸지 않는다.

## P3 프로토콜을 분리하는 이유

P3는 Lobby 프로토콜23과 `C6.P3.Lobby.*` 메시지, Game 봉투 버전23과 `C6.P3.State.v1`·`C6.P3.Control.v1`을 사용한다. 기존 Lobby10·Game11의2인 모드는 이전 씬에 남겨 둔다. 단순히 정원 숫자만 바꾸지 않고 명단과 상태 구조도 달라졌으므로, 다른 버전의 앱이 같은 방에 들어와 일부 상태만 이해하는 상황을 막기 위한 구분이다.

빌드 번호·프로토콜·Host 설정을 함께 확인하며, 화면에5인 표시가 있다는 사실만으로5인 게임 상태가 승인되는 것은 아니다. P3 씬의 Lobby·Game·Battle Controller 설정과 고정된 시작 명단이 모두 일치해야 한다. 패키지 업그레이드 없이 기존 NGO의 신뢰성 있는 분할 전송을 사용한다.
