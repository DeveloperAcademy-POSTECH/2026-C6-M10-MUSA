## 검사 시간이 사용되는 곳

최근 전체 실행 XML의 묶음 시간을 기준으로 반올림했다. 케이스 수가 많아도 즉시 끝나는 수치 검사는 적은 시간을 사용한다.

| 검사 묶음 | 케이스 | 시간 | 해당 모드 전체 시간 중 비중 |
| --- | ---: | ---: | ---: |
| EditMode `LabPaintSplatterConsistencyTests` | 24 | 약 11.90초 | 약 41.5% |
| EditMode `LabPaintSpreadFlowTests` | 43 | 약 10.67초 | 약 37.3% |
| PlayMode `LabOrbPhysicsTests` | 53 | 약 25.58초 | 약 24.5% |
| PlayMode `LabHangingPresentationTests` | 14 | 약 22.66초 | 약 21.7% |

EditMode의 두 도색 묶음이 전체 시간의 약 79%를 사용한다. 여러 해상도에서 형태·성장·완성을 계산하기 때문이다. PlayMode의 물리와 박 운동 두 묶음은 약 46%를 사용하며 실제 프레임·감쇠 시간을 기다린다. 이 실행 시간은 게임 플레이 중 FPS나 네트워크 지연의 성능 지표가 아니다.

단독 #240의 Mac 지연 환경은 실제 UDP 프록시의 편도 60ms·지터 ±10ms·데이터그램 1% 손실 확률이다. 실제 손실 기록도 확인했다. 참가자의 로컬 조합·비행 오브젝트는 입력 호출 안에서 생성됐고 Host의 조합 승인은 약 169~170ms 뒤 도착했다. 입력 호출 안에서 생성됐다는 것은 휴대폰 화면 표시나 터치 지연이 0ms라는 의미가 아니다.

## 중복 범위와 현재 한계

모델 검사와 PlayMode 검사가 같은 기능 이름을 다뤄도 검사하는 층이 다르다. 예를 들어 조합은 모델의 재료 소비·규칙, 보드의 드래그·Rigidbody, 네트워크 처리의 임시 ID 승격, 실제 앱 사이의 확정 전송을 각각 확인한다. 설정 공유도 수치 왕복과 실제 DEV 버튼/슬라이더 연결이 나뉜다. 이름만으로 중복이나 불필요함을 판단하기 어렵다.

과거 기능의 검사 일부는 현재 DEV 선택지나 설정 호환 계약을 유지하기 위한 것이다. 구형 모드·필드를 없애려면 생산 코드에서의 사용 여부와 유지할 계약을 먼저 결정해야 한다. 이번 분석으로 검사 삭제나 실행 정책을 변경하지 않았다.

현재 테스트 폴더에는 FPS·장시간 메모리·GC·실기기 응답 지연을 합격 기준으로 삼는 전용 성능 검사 묶음이 확인되지 않는다. 실제 진동 감각·사운드 품질·여러 실제 기기의 간섭·열·배터리도 별도 확인 범위다. `.github`에는 이슈·PR 양식만 있으며 자동 검사 workflow는 없으므로, 확인된 실행은 로컬 Unity CLI 실행이다.
